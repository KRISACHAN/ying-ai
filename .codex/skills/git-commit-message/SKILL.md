# Git Commit Message

## Workflow

1. Inspect the repository's commit rules first:
   - Read `commitlint.config.mjs` when present.
   - If it extends `@commitlint/config-conventional`, use Conventional Commits.
2. Determine the change source:
   - If `git diff --cached --quiet` exits nonzero, generate the message from staged changes only.
   - Otherwise generate the message from all working tree changes.
3. Gather context with direct Git commands.
4. Write one Chinese commit message with no AI attribution, no "generated by" trailer, and no assistant signature.
5. Validate the message with `pnpm commitlint` when available.
6. If the user only asked for a message, output only the final message in a fenced `text` block.
7. Run `git commit` only when the user explicitly asks to commit.

## Message Rules

Use this format unless the local commitlint config says otherwise:

```text
<type>(optional-scope): <subject>

<optional body>
```

Allowed default types:

- `feat`: user-facing feature or new capability
- `fix`: bug fix
- `docs`: documentation-only change
- `style`: formatting-only change
- `refactor`: code change that preserves behavior
- `perf`: performance improvement
- `test`: test change
- `build`: build system, dependency, or package manager change
- `ci`: CI configuration
- `chore`: tooling, maintenance, or housekeeping

Subject rules:

- Write the subject in Chinese.
- Use imperative mood.
- Keep it concise.
- Do not end with a period.
- Do not mention AI, Codex, ChatGPT, Claude, generated output, or co-authorship.
- Prefer one line for small changes.
- Add a body only when it clarifies multiple distinct changes or risk.

## Context Commands

Use direct commands; do not rely on helper scripts.

Inspect commit rules:

```bash
sed -n '1,120p' commitlint.config.mjs
```

Inspect status:

```bash
git status --short
```

Check for staged changes:

```bash
git diff --cached --quiet
```

If staged changes exist, inspect only staged changes:

```bash
git diff --cached --stat
git diff --cached --find-renames --find-copies
```

If no staged changes exist, inspect all working tree changes:

```bash
git diff --stat
git diff --find-renames --find-copies
git ls-files --others --exclude-standard
```

Avoid dumping very large lockfile diffs into context. For lockfiles, prefer `git diff --stat -- <lockfile>`.

## Source Selection

Staged changes take priority because they represent the user's intended commit scope.

If staged changes exist, ignore unstaged changes unless the user explicitly asks to include them.

If no staged changes exist, use all modified, deleted, renamed, and untracked files as the basis for the message.

## Validation

Validate without committing:

```bash
printf '%s\n' '<message>' | pnpm commitlint
```

If validation fails, revise the message until it passes.

## Commit Execution

Only commit when explicitly asked.

When committing, use the exact validated message:

```bash
git commit -m '<subject>'
```

For a multiline message, use multiple `-m` arguments.
