# AI Companion Core V1.3：Story Mode 实施阶段摘要

## 版本方案文件

```txt
.requirements/prompts/06-v1.3-story-mode-plan.md
```

版本目标：

> 在不破坏现有 Companion Chat 的前提下，新增可持久化、可恢复、可调试的文字互动故事模式。创作者能够定义故事背景、玩家身份、角色、场景、世界知识与叙事规则；用户的自由输入能够推动剧情，并产生受控、可追踪的世界状态变化。

V1.3 不把故事能力写进现有 `SimpleChatWorkflow`，而是新增独立的 Story Domain 与 Story Workflow。

```txt
packages/
├── ai-core
├── story-core
├── story-postgres
└── ...

apps/model-runtime-demo
├── Companion Workbench
└── Story Workbench
```

# Stage 01：Story Domain 与最小运行时

## 方案文件

```txt
.requirements/stages/v1.3/stage-01/01-story-domain-and-runtime-foundation.md
```

## 这个阶段做什么

建立故事功能的领域模型、扩展接口和最小可运行闭环，但暂时不接完整 UI 与数据库。

主要新增：

```txt
packages/story-core
```

核心契约包括：

```txt
StoryDefinition
PlayerRoleDefinition
StoryCharacterDefinition
SceneDefinition
LoreEntry
StorySession
StoryState
StoryStateChange
StoryTurnPlan

StoryProvider
StoryStateProvider
LoreProvider
StoryPlanner
StoryRenderer
StoryWorkflow
```

提供最小内置实现：

```txt
InMemoryStoryProvider
InMemoryStoryStateProvider
KeywordLoreProvider
ModelStoryPlanner
ModelStoryRenderer
DefaultStoryWorkflow
```

准备一个确定性的演示故事，例如：

```txt
雾港疑云
├── 固定玩家身份
├── 2～3 个角色
├── 2 个场景
├── 若干世界知识
├── 线索、关系值和事件状态
└── 明确的开场内容
```

最小调用链：

```txt
用户输入
↓
加载 Story Definition
↓
加载 Story State
↓
召回当前 Lore
↓
Story Planner 生成结构化 TurnPlan
↓
校验并应用 State Changes
↓
Story Renderer 生成最终文字
↓
保存新的 Story State
```

## 怎么做

`story-core` 依赖 `ai-core` 的通用能力：

```txt
ChatModel
SafetyProvider
CoreObserver
ToolRegistry（可选）
通用模型消息与流式能力
```

但 `ai-core` 不反向依赖 `story-core`。

Planner 必须输出结构化结果，不能让 Renderer 直接决定世界状态：

```ts
interface StoryTurnPlan {
  interpretedAction: StoryAction;
  activeCharacterIds: string[];
  narrativeBeat: NarrativeBeat;
  stateChanges: StoryStateChange[];
  triggeredEventIds: string[];
  revealedLoreIds: string[];
  responseGuidance: StoryResponseGuidance;
}
```

所有状态变更先通过确定性校验器：

```txt
允许修改的路径
允许执行的操作
字段数据类型
状态边界
事件是否重复
物品是否真实存在
场景切换条件是否满足
```

## 为什么这么做

故事模式最核心的不是 Prompt，而是领域边界和确定性状态。

先建立独立 `story-core`，可以避免：

```txt
Story / Scene / Lore 污染 ai-core
故事状态混入 Companion Memory
一个 Prompt 同时负责规划、写作与状态修改
UI 开发完成后才发现底层模型不稳定
```

这个阶段的完成标准是：

> 不依赖数据库和正式 UI，通过测试或脚本即可连续游玩若干回合，并保证场景、角色秘密、物品、关系值和事件状态不会随意失控。

# Stage 02：可控叙事工作流、Lore 与持久化

## 方案文件

```txt
.requirements/stages/v1.3/stage-02/02-narrative-workflow-lore-and-persistence.md
```

## 这个阶段做什么

将 Stage 01 的内存运行时升级为可恢复、可观测、可持久化的完整故事工作流。

主要完成：

```txt
1. DefaultStoryWorkflow 完整生命周期
2. 关键词 + 状态条件 Lore 召回
3. Story Session 与 Story State 持久化
4. 剧情摘要与上下文预算控制
5. Story Workflow Event
6. 失败、降级与一致性语义
```

新增：

```txt
packages/story-postgres
```

建议持久化以下内容：

```txt
stories
story_characters
story_scenes
story_lore_entries
story_sessions
story_session_states
story_messages
story_turns
story_summaries
```

## 怎么做

工作流固定为：

```txt
story:start
↓
Safety.guardInput
↓
StoryProvider.load
↓
StoryStateProvider.load
↓
LoreProvider.recall
↓
StoryPlanner.plan
↓
StateTransitionValidator.validate
↓
StoryRenderer.render / stream
↓
Safety.guardOutput
↓
StoryStateProvider.save
↓
StorySummaryUpdater.update
↓
story:finish
```

Lore V1 使用：

```txt
always 激活
keyword 激活
state condition 激活
scene / character 绑定
priority 与 token budget
```

暂时不把向量检索作为必需路径。关键词和状态条件更容易调试，也更适合关键秘密、场景门槛和剧情规则。

故事记忆严格分层：

```txt
Story Definition
创作者定义的永恒事实

Story State
物品、关系、线索、事件和当前场景等确定性事实

Narrative Summary
较长历史剧情的压缩摘要

Companion Memory
现实伴侣关系中的长期记忆
```

Story State 不通过现有 `MemoryProvider` 保存。当前 `MemoryScope` 虽然支持 `custom` owner，但其语义仍是长期记忆召回，并包含 `companionId`，不适合作为确定性故事状态仓库。

故事领域事件由 `story-core` 自己定义：

```txt
story:loaded
story:lore-recalled
story:plan-completed
story:state-changed
story:scene-changed
story:event-triggered
story:text-delta
story:finish
story:error
```

不要为了这些事件提前重构整个 `ai-core` 事件系统。

## 为什么这么做

这个阶段解决的是故事产品最容易出现的问题：

```txt
刷新后剧情丢失
模型忘记已经发生的事件
秘密提前泄露
角色知道不该知道的信息
死去角色重新出现
线索和物品凭空产生
长对话导致上下文无限膨胀
```

同时延续现有项目的 Provider / Adapter 模式：数据库连接和 SQL 留在外部包，Core 不读取环境变量、不直接连接数据库。当前 `ai-core` 也明确采用相同边界。

这个阶段的完成标准是：

> 故事可以持久化和恢复；连续多轮游玩后，世界状态仍然一致；调试数据能够说明某条 Lore 为什么被召回、某个事件为什么被触发、某项状态为什么发生变化。

# Stage 03：Story Workbench、创作体验与文档收口

## 方案文件

```txt
.requirements/stages/v1.3/stage-03/03-story-workbench-and-release-closure.md
```

## 这个阶段做什么

在现有 `model-runtime-demo` 中建立完整但克制的 Story Workbench，验证从“创作故事”到“开始游玩、继续存档”的完整用户路径。

最小用户路径：

```txt
创建故事
↓
配置玩家身份
↓
添加角色
↓
定义开场场景
↓
添加 Lore
↓
创建 Story Session
↓
进行故事对话
↓
查看状态与调试信息
↓
退出后继续故事
```

建议页面：

```txt
/stories
/stories/new
/stories/[storyId]/edit
/stories/[storyId]/sessions
/stories/[storyId]/sessions/[sessionId]
```

编辑器第一版只需要结构化表单，不做节点图：

```txt
基本信息
玩家身份
角色列表
场景列表
Lore 列表
叙事规则
开场预览
```

游玩页面包括：

```txt
故事标题与当前场景
文字对话区
用户输入 Composer
故事状态侧栏
角色关系与线索
调试抽屉
```

调试抽屉展示：

```txt
Effective Story Context
当前 Story State
召回的 Lore
Planner 原始结构化输出
通过校验的 State Changes
被拒绝的状态变化
当前场景与可用角色
剧情摘要
Workflow Timeline
模型 Runtime
```

## 怎么做

复用现有 Demo 的基础设施：

```txt
Next.js App Router
AI SDK UI useChat
自定义 Transport
NDJSON 流式协议
Wire Event Adapter
Run Debug Panel 的设计模式
PostgreSQL Debug Repository
```

当前 Demo 已经通过自定义 Transport 将 `core.streamWorkflow()` 的事件映射成 NDJSON 和 AI SDK UI message parts，因此 Story Mode 应复用这条技术路线，而不是另起一套 `streamText()` 协议。

新增平行链路：

```txt
POST /api/story-sessions/[sessionId]/messages
↓
storyWorkflow.stream()
↓
Story Workflow Event
↓
Story Wire Event
↓
Story UI Adapter
↓
AI SDK UIMessage
```

宿主负责根据会话类型选择 Runtime：

```txt
companion → CompanionCore / ChatWorkflow
story     → StoryRuntime / StoryWorkflow
```

不要把 Story Mode 作为 `SimpleChatWorkflow` 中的条件分支。

本阶段还要完成：

```txt
确定性契约测试
Postgres 集成测试
流式协议验证
连续多轮故事 E2E
刷新与恢复验证
README 与 AGENTS.md 更新
各 package README 更新
V1.3 完成状态同步
```

## 为什么这么做

故事模式不仅是后端能力，还需要验证创作者和玩家两条产品路径：

```txt
创作者能否理解如何配置故事？
玩家能否自然进入剧情？
状态变化是否可感知？
失败或模型异常时是否仍可恢复？
开发者能否定位剧情失控原因？
```

第一版不做可视化剧情树，是因为自由对话故事的核心价值是“状态驱动的叙事”，不是传统节点编辑器。过早开发节点画布会显著增加 UI 和数据模型复杂度，却不能证明故事运行时是否可靠。

这个阶段的完成标准是：

> 用户可以在 Demo 中创建或选择一个故事、开始新存档、进行多轮文字互动、刷新页面后继续故事，并通过调试面板完整查看 Lore、Planner、状态变化和模型输出过程。

# 三个 Stage 的依赖关系

```txt
Stage 01
Story Domain + 内存闭环
        ↓
Stage 02
可控 Workflow + Lore + PostgreSQL
        ↓
Stage 03
创作与游玩 Workbench + E2E + 文档
```

每个 Stage 的核心验收目标分别是：

```txt
Stage 01：故事能运行
Stage 02：故事能保持一致并恢复
Stage 03：故事能被创建、游玩和调试
```

# V1.3 明确不做

```txt
LangGraph
多 Agent
角色后台自主行动
可视化剧情节点画布
复杂战斗与数值系统
骰子系统
多人故事
故事分支复制与时间线回退
创作者市场
SillyTavern 角色卡完整兼容
向量 Lore 作为必需能力
自动生成完整故事
语音、图片或视频叙事
正式产品 UI 与商业化
```

V1.3 先证明一件事：

> 用户的自由输入能够可靠地改变故事世界，而故事世界的确定性状态能够持续约束后续叙事。
