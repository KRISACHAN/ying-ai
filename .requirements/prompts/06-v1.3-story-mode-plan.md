# AI Companion Core V1.3：Story Mode（文字互动叙事）实施方案

> 版本目标：在不破坏现有 Companion Chat 的前提下，新增可持久化、可恢复、可调试的**文字互动故事模式**（类 Charisma / AI 酒馆的叙事与角色对话，仅文字）。
>
> 创作者能定义故事背景、玩家身份、角色、场景、世界知识与叙事规则；玩家自由输入能推动剧情，并产生**受控、可追踪**的世界状态变化。
>
> V1.3 只聚焦本地开发与 SDK / Demo 能力；不引入用户系统、鉴权、部署、商业化与正式产品 UI。


### 对 `ai-core` 定位的诚实说明

长期愿景：`ai-core` 演进为跨域 **AI 运行时基座**（模型、工具、安全、观测、流式、通用 workflow 骨架），其上可挂伴侣、故事、知识库等域包。

**当前实情**：`ai-core` 仍以 Companion 语义为主（`CompanionCore`、`CompanionPersona`、`EmotionEngine`、`MemoryScope.companionId`、`SimpleChatWorkflow`）。V1.3 **不**做大拆包重命名。

正确做法：

```txt
复用 ai-core 中已通用的能力
  ChatModel / ModelProfile
  SafetyProvider
  CoreObserver（或同源观测习惯）
  ToolPlanning 的「结构化规划」模式
  流式 step runner 思路

新建 packages/story-core 承载故事域
  StoryDefinition / StoryState / Lore / StoryWorkflow

ai-core 不反向依赖 story-core
不把 Story State 塞进 MemoryProvider
不把 Companion Persona / Emotion / Memory 与 Story 互通（V1.3）
```

故事跑通后，若 Planner / Validator / 域 Workflow 模式稳定，再考虑把重复原语上提为真正的基座能力（可放后续版本，不阻塞 V1.3）。

## V1.3 核心目标

用户在 Demo 中选择（或导入）一个故事、开档游玩：

```txt
用户自由输入
↓
加载 Story Definition（开档快照）+ Story State
↓
按规则召回可见 Lore
↓
Story Planner 产出结构化 TurnPlan（含 stateChanges）
↓
StateTransitionValidator 确定性校验（全过或全拒）
↓
应用 State → Story Renderer 流式生成文字
↓
Safety.guardOutput → 持久化 State / Turn / Message
↓
Demo 展示叙事文本 + 状态侧栏 + Debug Timeline
```

V1.3 要证明的不是「Prompt 像不像酒馆」，而是：

> **自由输入能可靠改变故事世界；确定性世界状态能持续约束后续叙事。**

## 关键设计决定

### 1. 独立 Story Domain，宿主按会话类型选 Runtime

```txt
companion → CompanionCore / SimpleChatWorkflow
story     → StoryRuntime / StoryWorkflow（story-core）
```

禁止：

```ts
// SimpleChatWorkflow 内
if (mode === "story") { ... }
```

包布局目标：

```txt
packages/
├── ai-core              # 现有伴侣 Core（兼部分通用运行时）
├── story-core           # 新建：故事域 SDK
├── story-postgres       # 新建：故事持久化 Adapter
├── memory-postgres      # 不变：伴侣记忆
└── ...

apps/model-runtime-demo
├── Companion Workbench（已有）
└── Story Workbench（本版新增，克制）
```

### 2. Planner ≠ Renderer；状态只能由校验后的 Change 产生

对标现有 `ToolPlanningProvider`：**Planner 只产出结构化结果，禁止顺带写面向用户的长叙事。**

```ts
interface StoryTurnPlan {
  interpretedAction: StoryAction;
  /** 本回合参与叙事的角色；V1.3 默认仍输出单通道合并文本 */
  activeCharacterIds: string[];
  narrativeBeat: NarrativeBeat;
  stateChanges: StoryStateChange[];
  triggeredEventIds: string[];
  revealedLoreIds: string[];
  /** 行动被叙事内拒绝时填充；此时 stateChanges 应为空 */
  rejection?: StoryActionRejection;
  responseGuidance: StoryResponseGuidance;
}
```

```txt
Renderer 不得发明物品、线索、死亡、场景切换
被 Validator 拒绝的 change 不得部分应用（默认：整批拒绝）
非法 / 出戏行动：Planner 给出 rejection + guidance，Renderer 用戏内语气拒绝，不改世界
```

### 3. 核心状态固定 + 故事级自定义属性（表单不固定）

创作者需求：不同故事的「可配置字段」不同。例如武侠故事要「战斗力等级」，日常恋爱故事完全不需要；有的要「理智值 / 好感分段」，有的只要线索与场景。

V1.3 采用两层模型，而不是全局写死一张大表单：

```txt
Core State（所有故事共用，固定）
  场景、在场/存活、物品、线索、事件、基础关系槽等引擎必需字段

Attribute Schema（每个 StoryDefinition 自行声明）
  本故事有哪些自定义属性、类型、范围、作用于谁、是否在侧栏展示

Attribute Values（落在 StoryState.attrs）
  只允许出现 Schema 里声明过的 key；未声明的 key 校验失败
```

原则：

```txt
- 引擎不内置「战斗力」等业务字段；需要的故事在 Definition 里声明
- 不需要的故事不声明 → 表单 / 侧栏 / Planner 上下文都不出现该字段
- 禁止无 Schema 的任意 JSON 自由写（可扩展，但必须先声明再写入）
- Demo 若做定义预览或日后创作台：按 Attribute Schema 动态渲染控件，不写死字段列表
```

#### 3.1 Core StoryState

```ts
/** 开档时从 Definition 初始化；之后只允许合法 Change 修改 */
interface StoryState {
  schemaVersion: 1;
  storyId: string;
  /** 创建 session 时冻结的 definition 版本或内容哈希 */
  definitionVersion: string;
  currentSceneId: string;
  characters: Record<
    string,
    {
      alive: boolean;
      present: boolean;
    }
  >;
  inventory: string[];
  clues: string[];
  events: string[];
  /** 可选基础关系：characterId → number；是否启用由 Definition 声明 */
  relationships?: Record<string, number>;
  /** 故事级自定义属性实例；key 必须 ∈ Attribute Schema */
  attrs: Record<string, StoryAttrValue>;
  updatedAt: string; // ISO，Wire 友好；Core 内部可用 Date 再映射
}

type StoryAttrValue = boolean | number | string;

/**
 * attrs 的存储键必须可稳定寻址，建议规范：
 * - story 级：直接用 attribute.key，如 "clueHeat"
 * - player 级：`player:${key}`
 * - character 级：`character:${characterId}:${key}`
 * - scene 级：`scene:${sceneId}:${key}`
 * set_attr 校验时用 Schema.scope + scopeRef 生成同一套键，禁止模型自造键名。
 */
```

#### 3.2 Attribute Schema（写在 StoryDefinition 上）

```ts
type StoryAttrScope = "story" | "player" | "character" | "scene";

interface StoryAttributeDefinition {
  key: string; // 如 "combatPower" / "sanity" / "affectionTier"
  label: string; // 侧栏 / 表单展示名
  type: "boolean" | "number" | "string" | "enum";
  scope: StoryAttrScope;
  /** scope=character 时：适用角色 id；省略表示所有角色 */
  characterIds?: string[];
  required?: boolean;
  default?: StoryAttrValue;
  min?: number;
  max?: number;
  enumValues?: string[];
  /** 是否在游玩侧栏展示；默认 true */
  showInSidebar?: boolean;
  /** 是否允许本回合 Planner 修改；默认 true */
  writable?: boolean;
  description?: string;
}

interface StoryDefinition {
  // ... 背景、角色、场景、Lore、叙事规则等
  /** 本故事启用的自定义属性；空数组 = 无扩展字段 */
  attributes: StoryAttributeDefinition[];
  /** 是否启用核心 relationships 槽；默认 false 或按种子故事需要开启 */
  relationshipsEnabled?: boolean;
  relationshipBounds?: { min: number; max: number };
}
```

示例：

```txt
雾港疑云 attributes:
  - clueHeat（number, story）→ attrs["clueHeat"]
  - trust（number, character=lin）→ attrs["character:lin:trust"]
  （不声明 combatPower → 任何 set_attr(combatPower) 均失败）

武侠种子（若另做）attributes:
  - combatPower（number, character, min=0, max=100）
  - sectStanding（enum, player）
```

同一套引擎，两套表单；差异只来自 Definition，不来自改 Core 代码。

#### 3.3 StateChange：核心 op + 声明式属性写入

核心 op（引擎固定）：

```txt
set_scene
set_character_alive
set_character_present
add_inventory_item / remove_inventory_item
add_clue
add_event
set_relationship          # 仅当 relationshipsEnabled
```

扩展 op（仍受 Schema 约束，不是任意 path）：

```txt
set_attr
  key: string            # 必须在 attributes[] 中
  scopeRef?: string      # characterId / sceneId；story 级可省略
  value: StoryAttrValue
```

校验器必须检查：

```txt
核心 op 是否合法
set_attr 的 key 是否已在本故事 Attribute Schema 声明
writable !== false
type / min / max / enum 是否满足
scope 与 scopeRef 是否匹配（改角色属性必须带合法 characterId）
引用的 scene / character / item / clue / event 是否存在于 Definition
relationships 是否启用且在 bounds 内
事件是否重复触发
场景切换条件是否满足
死亡角色不得无故 present=true 且继续作为知情叙述者（按规则拒绝）
未声明的 attr key → 拒绝（防止模型发明「战斗力」污染无战斗故事）
```

### 4. Definition 在 Session 开档时冻结

```txt
创建 StorySession 时写入 definitionSnapshot（或 definitionVersion + 不可变内容）
之后创作者改种子故事，不影响已开档 session
V1.3 不做「热更新定义合并进旧存档」
```

### 5. 记忆严格分层；禁止复用 Companion Memory 存世界状态

```txt
Story Definition     创作者永恒事实（角色秘密、世界书条目）
Story State          物品、关系、线索、事件、当前场景（确定性）
Narrative Summary    长对话压缩摘要（类似 SummaryProvider 思路，但是故事域）
Companion Memory     现实伴侣关系记忆 —— V1.3 不读写
```

依据现状：`MemoryScope` 虽有 `ownerType: "custom"`，语义仍是长期记忆召回，且常见路径带 `companionId`，**不适合**作为确定性状态仓库。

### 6. Lore V1：关键词 + 状态条件，不做向量必选

```txt
always
keyword
state condition（依赖 StoryState）
scene / character 绑定
priority + token budget
```

秘密类 Lore 默认 `secret: true`，仅当 `revealedLoreIds` 或 state 条件满足时进入 Planner / Renderer 上下文。

### 7. 失败、降级与一致性（与 Companion 同等重要）

单回合推荐顺序（持久化时机必须写死）：

```txt
1. guardInput
2. load definition snapshot + state
3. recall lore
4. plan（失败 → 不改 state，返回 story:error，可重试同输入）
5. validate（任一 change 非法 → 整批拒绝，不改 state；可降级为「无状态变化 + 戏内拒绝」若 Planner 已给 rejection）
6. 在内存中 apply → 得到 nextState（尚未落库）
7. render / stream（失败 → 不落库 nextState；保留旧 state；返回可恢复错误）
8. guardOutput（拒绝 → 不落库 nextState）
9. 事务内保存：nextState + turn 记录 + messages（成功才提交）
10. 异步或同事务更新 Narrative Summary（失败不回滚已提交 turn，但要可观测）
```

其他约定：

```txt
- 默认不部分应用 stateChanges
- 同一 clientTurnId / idempotencyKey 重复提交：返回已有结果，不二次推进世界
- 流式中途断连：以是否完成步骤 9 为准；未提交则世界未变
- Planner 可用较小/较快模型；Renderer 用主聊天模型（宿主注入，Core 不读 env）
- 无状态变化的纯闲聊仍走 Planner（V1.3 不做短路径优化，避免双逻辑）
```

### 8. 事件分层：Story 自有 Core Event，Demo 再映射 Wire

不要为了故事事件重构整份 `ChatWorkflowStreamEvent`。

建议 Story Core Event（名称可在 stage 微调）：

```txt
story:start
story:loaded
story:lore-recalled
story:plan-completed
story:state-changed
story:scene-changed
story:event-triggered
story:text-delta
story:finish
story:error
```

Demo：

```txt
Story Core Event
↓
Story Wire Event（ISO 时间、剥离 raw）
↓
Story UI Adapter → AI SDK UIMessage parts
↓
游玩页 + Debug 抽屉
```

复用现有技术路线：`chat-stream-wire.ts` / `demo-chat-transport.ts` / `chat-stream-ui-adapter.ts` 的**模式**，而不是把故事事件硬塞进 Companion Wire 联合类型（可平行模块，例如 `story-stream-wire.ts`）。

### 9. Stage 03 先证明运行时，创作台保持克制

V1.3 Demo 最小路径：

```txt
选择种子故事（雾港疑云）或导入 StoryDefinition JSON
↓
创建 / 继续 Session
↓
文字游玩
↓
状态侧栏 + Debug（Lore / Plan / Changes / Timeline / Runtime）
↓
刷新后恢复
```

```txt
必须有：游玩 + 续档 + Debug
可以有：极简 JSON 导入 / 只读定义预览
状态侧栏：只展示本故事 Attribute Schema 中 showInSidebar 的字段 + 核心场景/物品/线索
明确可延后到 V1.4：按 Schema 动态生成的完整创作表单、属性编辑器、多故事 CRUD
```

第一版不做节点画布：自由对话故事的核心是**状态驱动叙事**，不是传统 AVG 节点编辑器。创作台若后续补齐，控件必须由 `attributes[]` 驱动，禁止为「战斗力」等字段写死专用表单项。

### 10. 与「基座」愿景的关系（写进范围，避免范围漂移）

```txt
V1.3：用 story-core 验证「域包 + 复用运行时」是否成立
V1.x 之后：若模式稳定，再抽 ai-runtime / 上提共享原语
知识库：同构为未来 knowledge-core，本版不实现
```


## 怎么做

- `story-core` 依赖 `@ying-companion/ai-core` 的 **公开通用类型/接口**（`ChatModel`、`SafetyProvider`、消息类型等），不依赖 `SimpleChatWorkflow` 内部模块。
- Planner 调用应走能力声明友好路径（需要可靠结构化输出时，在 stage 中明确 `generate` 约束与解析失败语义，对标 `DefaultToolPlanningProvider`）。
- 用确定性脚本 / `verify:*` 契约测试跑「雾港疑云」多回合：断言 inventory / clues / scene / secret 可见性。

## 完成标准

> 不依赖数据库和正式 UI，通过脚本即可连续游玩若干回合；场景、秘密、物品、关系值、事件不会随意失控；非法行动不静默改世界；**未在 Attribute Schema 声明的自定义字段写入必须被拒绝**。
