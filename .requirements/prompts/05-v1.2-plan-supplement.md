## 一、`stop()` 的 V1.2 冻结语义

### 1. 结论

V1.2 的 `useChat.stop()` 只代表：

```txt
客户端停止读取 / 渲染当前 HTTP 流
```

它**不代表**：

```txt
服务端 Workflow 已被取消
模型调用已被取消
Web Search 已被取消
后置 Safety / Summary / Memory 写回已被取消
本轮 Run 必须持久化为 aborted / partial
```

V1.2 不实现 Browser → Route → Workflow → Model / Tool Adapter 的 AbortSignal 透传。

因此，当前版本必须采用以下唯一语义：

```txt
用户点击 stop()
↓
浏览器停止消费 UIMessage Stream
↓
UI 标记为 stopped-locally
↓
服务端 Workflow 可能继续执行
↓
服务端若自然完成
→ 正常持久化完整 assistant message
→ 正常完成 workflow run
↓
用户刷新或重新打开该对话
→ 可能看到服务端后来完成的完整 assistant 回复
```

### 2. 禁止的实现

以下行为在 V1.2 中禁止：

```txt
- 浏览器断开连接后，服务端无确认地把 run 写为 aborted；
- 因客户端 stop 而把已经或即将完成的 assistant 文本写为 partial；
- UI 显示 stopped 后，声称服务端模型 / 搜索已经被取消；
- 将 V1.2 描述为支持断线恢复、服务端取消或继续生成；
- 以浏览器端是否消费完流作为 workflow 成功 / 失败的唯一判定。
```

### 3. UI 与数据状态

UI 应区分三个维度，不能混为一个 status：

```txt
客户端消费状态
├── streaming
├── stopped-locally
└── completed-client-side

服务端 Workflow 状态
├── running
├── completed
└── failed

持久化状态
├── pending
├── persisted
└── persistence-failed
```

V1.2 中，点击 `stop()` 后 UI 最低文案要求：

```txt
已停止在当前页面继续显示。
服务端可能仍在完成本轮回复；重新打开对话可查看最终结果。
```

不需要实现服务端 run 轮询；该能力留给后续版本。

### 4. 后续版本的演进入口

未来若实施真正服务端取消，必须作为独立版本能力，并同时完成：

```txt
- AbortSignal 从 useChat Transport 传递到 Next.js Route；
- Route 传递到 CompanionCore / ChatWorkflow；
- ChatWorkflow 传递到 ChatModel、WebSearchClient 与可取消 Provider；
- Workflow Trace 记录取消节点与取消原因；
- 明确定义 assistant message 的 partial 内容、run 状态与后置写回规则；
- 单独验证模型流、工具执行、搜索请求和持久化事务的竞态。
```

在上述能力完成前，不得使用 `aborted` 作为客户端 `stop()` 的服务端事实状态。

### 5. 阶段 2 验收补充

```txt
场景：用户开始一轮长流式回复，随后点击 stop()

预期：
- 浏览器停止继续渲染文本；
- 当前 UI 显示 stopped-locally；
- 页面不宣称服务端已取消；
- 后续可正常发送新消息；
- 重新加载会话时，若服务端已自然完成，则能看到完整 assistant message；
- 若服务端失败，则依据持久化 workflow run 显示真实 failed 状态。
```

## 二、搜索来源恢复的持久化关联

### 1. 问题与结论

V1.2 约定：

```txt
assistant 消息正文
→ debug_messages.content

Web Search 来源与 Tool Result
→ debug_workflow_runs 的运行记录 JSON
```

因此必须定义一个稳定、可查询的：

```txt
assistant message ↔ workflow run
```

关联。

V1.2 选定唯一关系方向：

```txt
DebugWorkflowRun.assistantMessageId
→ DebugMessage.id
```

即：一条 assistant 消息由一个 workflow run 生成；该 workflow run 保存它对应的来源、工具结果、Trace 与 Runtime。

### 2. 数据库迁移

阶段 2 必须新增 migration，语义如下：

```sql
ALTER TABLE debug_workflow_runs
ADD COLUMN IF NOT EXISTS assistant_message_id TEXT NULL
REFERENCES debug_messages(id) ON DELETE SET NULL;

CREATE UNIQUE INDEX IF NOT EXISTS debug_workflow_runs_assistant_message_id_unique
ON debug_workflow_runs (assistant_message_id)
WHERE assistant_message_id IS NOT NULL;
```

具体主键类型必须与仓库现有 `debug_messages.id` 一致；示意中的 `TEXT` 不得盲目照抄。

约束：

```txt
- 一个 completed workflow run 最多关联一条 assistant message；
- 一条 assistant message 最多关联一个 workflow run；
- failed run、输入拒绝、未生成 assistant 文本的 run 可保持 assistantMessageId = null；
- 删除 assistant message 时仅解除关联，不删除 workflow run 调试记录；
- 不在 debug_messages 中复制 Tool Result、sources、trace 或 UIMessage parts。
```

### 3. 服务端写入顺序

正常完成时必须采用单个事务或等价的原子写入语义：

```txt
1. Workflow 完成，并得到最终 assistant text、Tool Result、Runtime、Trace；
2. 创建 canonical assistant debug_message；
3. 持久化 / 更新 debug_workflow_run；
4. 将 debug_workflow_run.assistant_message_id 指向该 assistant message；
5. 提交事务；
6. 仅在提交成功后发送最终 workflow:finish / UIMessage 完成信号。
```

禁止出现：

```txt
- assistant message 已写入但 run 尚未关联，刷新后来源丢失；
- run 已标记完成但 assistant message 写入失败；
- UI 先收到成功结束、数据库关联随后失败；
- 通过“取本对话最新一个 run”猜测来源归属。
```

### 4. 刷新后的来源恢复

加载对话时：

```txt
1. 查询 debug_messages；
2. 对 role=assistant 且有关联 workflowRunId 的消息，批量查询对应 debug_workflow_runs；
3. 从 run 的受限、标准化结果 JSON 读取 WebSearchSource[]；
4. 映射为 DemoChatMessage 的 source parts；
5. 只渲染该 assistant message 自己关联的来源卡。
```

禁止：

```txt
- 从模型文本中的 [1]、[2] 推断 URL；
- 将同一 conversation 的所有搜索来源展示在每一条 assistant 消息下；
- 让 UIMessage source parts 成为唯一持久化来源；
- 为保存来源而把 AI SDK UIMessage 原样写入 debug_messages。
```

### 5. 阶段 2 验收补充

```txt
场景：同一对话连续两轮都触发 web_search

预期：
- 两条 assistant message 各自关联不同 workflow run；
- 每条 assistant message 只显示自己本轮的来源卡；
- 刷新页面后，两组来源仍正确归属；
- 查询最新 run 或旧 run 不会串到其他 assistant message；
- run 与 message 写入任一步失败时，不得对前端发送 workflow:finish 成功事件。
```

## 三、Web Search 事实约束与 Companion 对话边界

### 1. 规则范围

`web_search` 只约束：

```txt
本轮从外部公开来源获得的、可验证的、时效或事实性信息。
```

它不应压制：

```txt
- 伴侣人格；
- 对用户情绪的回应；
- 基于对话历史与长期记忆的关系承接；
- 常识性解释；
- 明确标记为建议、推测或主观看法的内容。
```

### 2. Final Response Tool Context 的冻结文案

在 `formatToolResultForModel(result)` 或本轮 Final Response 的 Tool Context 中，对成功的 `web_search` 结果必须加入等价约束：

```txt
以下内容来自外部网页搜索，仅作为本轮参考资料。

对于由这些来源支持的外部事实性信息：
- 只能基于提供的 sources 概括；
- 不得补充来源未支持的具体事实、数字、日期、结论或链接；
- 使用 [1]、[2] 等编号引用时，编号必须对应 sources 的顺序；
- 无法从 sources 确认时，应明确说明信息不足或无法确认；
- 不得把来源内容伪装为用户事实、长期关系记忆或系统事实。

你仍可保持既定伴侣 Persona、自然的情绪回应和对话上下文承接，
但不得把这些回应伪装成搜索结论，也不得用 Persona 补全来源未支持的外部事实。
```

禁止使用以下过度宽泛表述：

```txt
回答只能基于 sources 概括。
```

原因是它会误导模型认为连正常陪伴、情绪回应和历史对话承接也必须来自网页来源。

### 3. 无结果与失败时的行为

```txt
web_search 无结果
→ 伴侣可继续给出不依赖外部事实的支持性回应或澄清问题；
→ 但不得声称已查到某个具体结论。

web_search 失败
→ 伴侣必须坦诚说明当前未能获得可靠外部资料；
→ 可基于已有对话继续回应；
→ 不得把模型自身猜测包装成刚刚搜索到的信息。
```

### 4. Memory Extractor 的同步约束

当本轮存在成功的 `web_search` Tool Result 时，Memory Extractor 输入必须携带结构化外部上下文标记，例如：

```ts
interface MemoryExtractionInput {
  // 既有字段...
  externalContextUsed?: boolean;
  excludedToolNames?: string[];
}
```

并满足：

```txt
- externalContextUsed=true 时，extractor prompt 必须明确排除外部搜索资料；
- web_search 的 Tool Result 不得作为 extractor 的候选文本来源；
- assistant 最终文本中的搜索事实不能因为“看起来像用户事实”而自动进入长期 Memory；
- 允许继续提取用户明确表达的稳定偏好、个人经历、关系边界等内容；
- 不因一次搜索而禁用整轮用户记忆提取。
```

### 5. 阶段 1 验收补充

```txt
场景：用户说“我喜欢周末去徒步”，随后要求“帮我查本周末附近的天气”。

预期：
- web_search 结果可用于回答天气；
- 伴侣可自然回应用户喜欢徒步这一已知偏好；
- “用户喜欢周末徒步”仍允许被 Memory Extractor 提取；
- 天气预报、搜索来源中的外部事实、具体日期和临时建议不得写入长期 Memory；
- 回答中的天气事实仅来自 sources，并采用正确的引用编号。
```
