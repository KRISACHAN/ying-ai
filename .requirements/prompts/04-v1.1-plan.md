# AI Companion Core V1.1 实施方案

> 版本目标：在 V1.0 Core SDK 的基础上，完成「工作流级流式聊天、Persona 扩展、多模型 Provider 策略与 Ollama 接入、调试工作台升级、文档同步」。
>
> V1.1 仍然只聚焦本地开发与 Core / SDK 能力；不引入用户系统、鉴权、部署、商业化与产品正式 UI。

---

## 前置基线

V1.1 以 `prod` 分支中已完成的 V1.0 为唯一实现基线。

V1.0 已具备：

```txt
Model Runtime
├── OpenAI-compatible 模型实现
├── generate / stream
├── 主模型重试
├── fallback 模型
└── runtime 信息

AI Core SDK
├── Provider 抽象与注入
├── Persona
├── Safety
├── Memory / RAG
├── Emotion
├── Tool Registry
├── Summary
├── SimpleChatWorkflow
└── CoreObserver / Workflow Trace

Debug Workbench
├── 本地模型配置
├── 会话与消息持久化
├── 记忆、情绪、摘要查看
└── Workflow / Runtime 可观测信息
```

V1.1 不重做 V1.0 的 Provider 边界，也不将第三方 SDK、数据库、环境变量直接写入 `packages/ai-core`。

---

## V1.1 核心目标

将当前「完整执行后一次性返回回复」的 Core，升级为：

```txt
可选择模型 Provider
↓
可配置伴侣 Persona
↓
可执行完整聊天工作流
↓
可向宿主连续输出结构化流事件
↓
用户看到伴侣回复逐字生成
↓
流结束后完成 Safety、Summary、Memory 写回与最终结果收口
```

V1.1 完成后，宿主应可以：

1. 在 Demo 中配置伴侣对用户的称呼；
2. 在 Demo 中配置伴侣的扩展设定，例如身高、体重、爱好、发型、身材；
3. 在 Demo 中选择 OpenAI-compatible 或 Ollama 模型；
4. 在 Demo 中看到真实流式聊天回复；
5. 在 Demo 中查看本次工作流的事件、模型 runtime、最终 Persona、Prompt、记忆、情绪、工具执行与写回结果；
6. 在不修改 `ai-core` 业务逻辑的前提下，继续新增其他模型 Adapter。

## 阶段 1：V1.1 契约与兼容边界

### 目标

先定义 V1.1 的公共 API、事件模型和兼容策略，再开始改动工作流实现。

### 完成标准

- 明确 `executeWorkflow()` 与 `streamWorkflow()` 的职责；
- 明确流事件的类型、顺序、错误语义与完成语义；
- 明确流式工作流中 Tool、Safety、Summary、Memory 的执行边界；
- 明确旧 API 不删除、旧宿主不会因 V1.1 升级而失效；
- 新增 V1.1 stage 文档目录与对应验收标准。

### 01-v1.1-contract.md

#### 要做成什么样

Core 应同时提供两条稳定调用路径：

```ts
core.executeWorkflow(input)
core.streamWorkflow(input)
```

职责约定：

```txt
executeWorkflow
→ 返回完整 ChatWorkflowOutput
→ 适合后台任务、结构化处理、旧宿主兼容、非流式调试

streamWorkflow
→ 返回 AsyncIterable<ChatWorkflowStreamEvent>
→ 适合前台聊天 UI 与实时调试面板
→ 最后必须发送 workflow:finish，携带完整 ChatWorkflowOutput
```

#### 流事件建议

```ts
type ChatWorkflowStreamEvent =
  | { type: "workflow:start"; workflowId: string; timestamp: Date }
  | { type: "step:start"; workflowId: string; step: WorkflowStepName; timestamp: Date }
  | { type: "step:end"; workflowId: string; step: WorkflowStepName; timestamp: Date; summary?: Record<string, unknown> }
  | { type: "text:delta"; workflowId: string; text: string; model?: string }
  | { type: "tool:call"; workflowId: string; call: ModelToolCall }
  | { type: "tool:result"; workflowId: string; result: ToolResult }
  | { type: "workflow:finish"; workflowId: string; output: ChatWorkflowOutput }
  | { type: "workflow:error"; workflowId: string; error: SafeWorkflowError };
```

#### 流式与工具调用边界

V1.1 采用以下策略：

```txt
Persona / Safety / Summary / Memory / Emotion
↓
工具决策与工具执行
↓
必要时使用 generate 完成工具循环
↓
工具循环结束后
↓
最终自然语言回答使用 stream 输出
↓
Output Safety 审计
↓
Summary / Memory 写回
↓
workflow:finish
```

约束：

1. V1.1 不实现“已经开始吐字后再插入工具调用”；
2. V1.1 不实现“已经开始吐字后切换 fallback 模型继续拼接”；
3. 流式模型在首个文本 delta 前失败，可按 Model Runtime 的策略重试或 fallback；
4. 已经发送 `text:delta` 后的模型异常，必须发出 `workflow:error`，不得伪装为成功；
5. `workflow:finish` 只在输出安全审计、摘要更新、记忆写回完成或按既有降级策略处理后发送。

#### 可观测结果

在 Demo 的事件时间线中，至少可看到：

```txt
workflow:start
step:start / step:end
text:delta × N
workflow:finish
```

并能确认：

- 旧 `executeWorkflow()` 仍可调用；
- 新 `streamWorkflow()` 能被独立消费；
- 流结束后可以获得完整 `ChatWorkflowOutput`。

## 阶段 2：模型 Provider 策略与能力声明

### 目标

让 Core 不依赖具体供应商 SDK，并让工作流能够判断当前模型是否支持流式、工具调用、usage 等能力。

### 完成标准

- `ChatModel` 增加稳定能力声明；
- 宿主配置可区分 OpenAI-compatible 与 Ollama；
- `createModel(config)` 根据配置策略创建对应 Adapter；
- Provider 差异不泄漏到 Workflow 业务逻辑；
- 现有 OpenAI-compatible 配置保持兼容。

### 02-model-provider-strategy.md

#### 要做成什么样

建议在 Core 抽象层新增：

```ts
interface ModelCapabilities {
  streaming: boolean;
  toolCalling: boolean;
  usage: boolean;
}

interface ChatModel extends CoreProvider {
  readonly capabilities: ModelCapabilities;
  generate(input: GenerateInput): Promise<GenerateOutput>;
  stream(input: GenerateInput): AsyncIterable<GenerateStreamChunk>;
}
```

宿主侧模型配置使用判别联合：

```ts
type ModelConfig =
  | OpenAICompatibleConfig
  | OllamaConfig;
```

示意：

```ts
type OpenAICompatibleConfig = {
  provider: "openai-compatible";
  apiKey: string;
  baseUrl?: string;
  model: string;
  fallbackModel?: string;
  retry?: ModelRetryConfig;
};

type OllamaConfig = {
  provider: "ollama";
  host?: string;
  model: string;
  keepAlive?: string;
};
```

#### 为什么要做

V1.0 的 `OpenAICompatibleModel` 不能成为 Core 唯一模型实现。V1.1 要使：

```txt
Core / Workflow
→ 只依赖 ChatModel

宿主 / Factory
→ 负责选择 OpenAI-compatible 或 Ollama
```

这样未来增加 Anthropic、Gemini、其他本地模型时，只需增加 Adapter 与配置策略。

#### 可观测结果

Demo 的模型面板可显示：

```txt
provider: openai-compatible | ollama
model: ...
capabilities:
  streaming: true
  toolCalling: true | false
  usage: true | false
```

## 阶段 3：工作流级流式协议与 SimpleChatWorkflow 流式化

### 目标

把“模型级 stream”升级为“Core / Workflow 级 stream”，让宿主可以消费完整聊天生命周期，而不只是消费文本。

### 完成标准

- `ChatWorkflow` 支持流式执行；
- `CompanionCore` 提供 `streamWorkflow()`；
- `SimpleChatWorkflow` 能逐步产出事件；
- 伴侣最终回答能真实流式输出；
- 现有 trace、observer、runtime、summary、memory、emotion、tool 结果仍可在流结束后得到；
- 流失败语义明确，不吞错误。

### 03-streaming-workflow.md

#### 要做成什么样

建议扩展工作流接口：

```ts
interface ChatWorkflow extends CoreProvider {
  execute(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): Promise<ChatWorkflowOutput>;

  stream(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

`CompanionCore` 转发为：

```ts
core.executeWorkflow(input)
core.streamWorkflow(input)
```

#### 关键实现原则

1. 不要把 `execute()` 简单复制一份到 `stream()`，避免两个主链路逐渐漂移；
2. 应抽取共享的前置准备、Prompt 构建、工具执行、结果收口逻辑；
3. `execute()` 与 `stream()` 只在“最终自然语言生成与事件输出方式”上分支；
4. 事件应是公开稳定契约，Demo 不应解析内部 console 文本；
5. `CoreObserver` 继续作为旁路观测，不替代 `streamWorkflow()` 的宿主消费协议。

#### 输出安全边界

V1.1 中 Output Safety 保持“完整文本后审计”：

```txt
text:delta 已输出
↓
流完成
↓
得到完整 assistant text
↓
Safety.guardOutput
```

若 Output Safety 拒绝：

- 必须发送 `workflow:error`；
- Demo 必须明确标记该条回复未通过最终审计；
- 不返回伪造的安全回复；
- 不隐瞒已经展示给用户的部分文本。

实时 token 级安全过滤属于后续版本能力，不纳入 V1.1。

#### 可观测结果

Demo 聊天窗口中：

```txt
用户发送消息
↓
伴侣回复逐字出现
↓
流结束后显示 final 状态
↓
侧边调试面板显示：
- workflow trace
- runtime
- memory recall
- emotion
- tool calls / results
- summary / memory writeback
```

## 阶段 4：Persona 扩展与 Prompt 构建升级

### 目标

使 Persona 不再只包含名称、性别、性格和说话风格，而是能表达伴侣对用户的称呼与更完整的外在、兴趣设定。

### 完成标准

- `CompanionPersona` 支持用户称呼；
- `CompanionPersona` 支持外貌与兴趣设定；
- 默认 Persona 与旧配置保持兼容；
- Prompt Builder 只渲染有效字段；
- Demo 可编辑并实时使用这些配置；
- 调试面板可查看最终生效 Persona 与最终 system prompt。

### 04-persona-profile.md

#### Persona 扩展建议

```ts
interface CompanionPersona {
  id: string;
  name: string;
  gender: CompanionGender;

  relationship?: string;
  personality?: string;
  speakingStyle?: string;
  background?: string;
  systemPrompt?: string;

  userDisplayName?: string;
  userAddress?: string;

  profile?: {
    hobbies?: string[];
  };

  appearance?: {
    heightCm?: number;
    weightKg?: number;
    hair?: string;
    bodyType?: string;
    additionalTraits?: Record<string, string>;
  };

  metadata?: Record<string, unknown>;
}
```

#### 字段约定

```txt
userDisplayName
→ 用户名字，例如：陈大鱼头

userAddress
→ 伴侣对用户的日常称呼，例如：鱼头、亲爱的、宝贝、先生

profile.hobbies
→ 伴侣自己的兴趣爱好，例如：电影、烘焙、旅行

appearance.heightCm / weightKg
→ 使用明确数值单位，避免 prompt 解释歧义

appearance.hair / bodyType
→ 面向自然语言描述，例如：黑色长直发、匀称

appearance.additionalTraits
→ 承接后续可扩展描述，例如：瞳色、穿衣风格、声音、常用饰品
```

#### Prompt 构建原则

1. 系统提示词中必须把“伴侣自身设定”与“用户信息”区分清楚；
2. `userAddress` 是建议称呼，不应强制每句话都使用；
3. Persona 字段缺失时不输出“未知”“未设置”等噪音；
4. `systemPrompt` 如存在，应作为补充指令而非绕过结构化 Persona；
5. 不把长篇静态 Persona 重复拼入 Summary 或 Memory。

#### 可观测结果

Demo 中配置：

```txt
用户称呼：鱼头
伴侣爱好：烘焙、电影
身高：165 cm
发型：黑色长直发
身材：匀称
```

然后确认：

```txt
1. Prompt Preview 可看到完整 Persona 描述；
2. 伴侣回复可自然使用“鱼头”；
3. 伴侣可在合适话题中提及自己的兴趣或设定；
4. 未配置字段不会污染 prompt。
```

## 阶段 5：Ollama Adapter

### 目标

增加正式的 Ollama `ChatModel` Adapter，使本地模型可注入 V1.1 Core，而不是通过 OpenAI-compatible 模拟接入。

### 完成标准

- 新增独立 `model-ollama` package；
- 使用 `ollama` npm 包实现 `ChatModel`；
- 支持 `generate()` 与 `stream()`；
- 支持宿主配置 host、model、keepAlive；
- 对工具调用能力做明确映射或显式能力降级；
- OpenAI-compatible 与 Ollama 使用同一套 Core / Workflow API；
- Demo 可切换两个 Provider。

### 05-ollama-model-adapter.md

#### 包边界

```txt
packages/
├── ai-core/
│   ├── ChatModel 抽象
│   ├── Workflow
│   └── 流协议
│
├── model-ollama/
│   ├── OllamaChatModel
│   ├── OllamaConfig
│   └── Ollama message / tool 映射
│
└── memory-postgres/
```

约束：

```txt
- ollama npm 依赖不得进入 ai-core
- ai-core 不得读取 OLLAMA_HOST / OLLAMA_MODEL
- 宿主负责读取环境变量或表单配置，再创建 OllamaChatModel
- Workflow 不得直接判断 provider 名称，只通过 ChatModel.capabilities 行为分支
```

#### 运行时语义

```txt
OpenAI-compatible
→ 保留既有 retry / fallback / runtime 语义

Ollama
→ 先实现单模型本地调用与流式输出
→ runtime 中明确 provider、model、attempts
→ 若不支持 fallback，不虚构 fallback 状态
```

#### 工具调用边界

Ollama 模型与模型版本对 tool calling 的支持可能不同。

V1.1 必须：

1. 在 `capabilities.toolCalling` 中明确声明；
2. 若当前模型不支持工具调用，工作流必须跳过工具路径并发送可观测事件或 trace 标记；
3. 不得让模型“不支持 tool calling”变成难以定位的 prompt 或解析异常；
4. 不要求所有 Ollama 模型在 V1.1 中都通过工具调用验收。

#### 可观测结果

在本地 Ollama 服务正常运行时：

```txt
Demo 选择 provider = ollama
↓
填写 host / model
↓
发送聊天消息
↓
看到逐字输出
↓
最终查看 workflow:finish
↓
确认 Persona / Memory / Emotion 仍然生效
```

## V1.1 关键设计原则

1. `streamWorkflow()` 是新增公开 API，不替换或删除 `executeWorkflow()`；
2. 模型级流与工作流级流必须区分，宿主应消费工作流事件而不是直接消费模型文本；
3. 最终用户可见回复流式化，内部结构化任务仍允许使用非流式 `generate()`；
4. 流式工具调用采用“先完成工具循环，再流式最终回答”的稳定策略；
5. Persona 是 Core 配置，不依赖用户系统；
6. `userAddress` 是伴侣对用户的称呼，而不是未来用户体系中的账号昵称；
7. 外部 SDK Adapter 必须独立 package，`ai-core` 保持纯 SDK；
8. Workflow 不通过 provider 名称写分支，只通过模型能力声明决定行为；
9. 所有模型配置由宿主读取和注入，`ai-core` 不读取环境变量；
10. Demo 是长期保留的调试工作台，不是一次性临时页面；
11. 任何流式失败都必须可观测、可定位，不得用伪成功掩盖；
12. 每个阶段完成后必须有可复现的人工验证结果与 review 归档。
