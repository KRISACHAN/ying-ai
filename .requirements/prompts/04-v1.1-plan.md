# AI Companion Core V1.1 实施方案

> 版本目标：在 V1.0 Core SDK 的基础上，完成「Persona 扩展与称呼、工作流级流式聊天、多模型 Provider 策略与 Ollama 接入、调试工作台升级、文档同步」。
>
> V1.1 仍然只聚焦本地开发与 Core / SDK 能力；不引入用户系统、鉴权、部署、商业化与产品正式 UI。

---

## 前置基线

V1.1 以 `prod` 分支中已完成的 V1.0（tag `v1.0`）为唯一实现基线。

V1.0 已具备：

```txt
Model Runtime
├── OpenAI-compatible 模型实现
├── generate / stream
├── 主模型重试
├── fallback 模型
└── runtime 信息

AI Core SDK
├── Provider 抽象与注入
├── Persona
├── Safety
├── Memory / RAG
├── Emotion
├── Tool Registry
├── Summary
├── SimpleChatWorkflow
└── CoreObserver / Workflow Trace

Debug Workbench
├── 本地模型配置
├── 会话与消息持久化
├── 记忆、情绪、摘要查看
└── Workflow / Runtime 可观测信息
```

V1.1 不重做 V1.0 的 Provider 边界，也不将第三方 SDK、数据库、环境变量直接写入 `packages/ai-core`。

## V1.1 核心目标

将当前「完整执行后一次性返回回复」的 Core，升级为：

```txt
可选择模型 Provider
↓
可配置伴侣 Persona（含用户称呼与外貌兴趣设定）
↓
可执行完整聊天工作流
↓
可向宿主连续输出结构化流事件
↓
用户看到伴侣回复逐字生成
↓
流结束后完成 Safety、Summary、Memory 写回与最终结果收口
```

V1.1 完成后，宿主应可以：

1. 在 Demo 中配置伴侣对用户的称呼、用户显示名，以及身高、体重、发型、身材、爱好等扩展设定；
2. 在 Demo 中选择 OpenAI-compatible 或 Ollama 模型；
3. 在 Demo 中看到真实流式聊天回复；
4. 在 Demo 中查看本次工作流的事件、模型 runtime、最终 Persona、Prompt、记忆、情绪、工具执行与写回结果；
5. 在不修改 `ai-core` 业务逻辑的前提下，继续新增其他模型 Adapter。

## 阶段 1：Persona 扩展与 Prompt 构建升级

### 目标

使 Persona 不再只包含名称、性别、性格和说话风格，而是能表达伴侣对用户的称呼与更完整的外在、兴趣设定。此阶段与流式改造完全独立，最先交付。

### 完成标准

- `CompanionPersona` 新增 `userDisplayName`、`userAddress` 字段；
- `CompanionPersona` 新增 `profile.hobbies`、`appearance` 扩展分组；
- 现有 Persona 字段与默认实现保持向后兼容（旧配置不传新字段即可）；
- Prompt Builder 只渲染有效字段，缺失字段不输出"未知""未设置"噪音；
- `systemPrompt` 字段若存在，作为补充指令而非绕过结构化 Persona；
- Demo 可编辑并实时使用这些配置；
- 调试面板可查看最终生效 Persona 与完整 system prompt。

### 01-persona-profile.md

#### Persona 扩展

```ts
interface CompanionPersona {
  id: string;
  name: string;
  gender: CompanionGender;

  // V1.0 已有字段，保持不变
  relationship?: string;
  personality?: string;
  speakingStyle?: string;
  background?: string;
  systemPrompt?: string;

  // V1.1 新增：用户信息
  userDisplayName?: string; // 用户的名字，例如：陈大鱼头
  userAddress?: string; // 伴侣对用户的日常称呼，例如：鱼头、宝贝

  // V1.1 新增：伴侣兴趣
  profile?: {
    hobbies?: string[]; // 伴侣自己的兴趣，例如：烘焙、电影、旅行
  };

  // V1.1 新增：伴侣外貌
  appearance?: {
    heightCm?: number; // 使用明确数值单位，避免 prompt 解释歧义
    weightKg?: number;
    hair?: string; // 面向自然语言，例如：黑色长直发
    bodyType?: string; // 例如：匀称
    additionalTraits?: Record<string, string>; // 瞳色、穿衣风格等后续扩展
  };

  metadata?: Record<string, unknown>;
}
```

#### 字段约定

```txt
userDisplayName
→ 用户名字，用于伴侣在 Persona 中了解自己在与谁说话

userAddress
→ 伴侣对用户的日常称呼，是建议称呼，不强制每句话都使用

profile.hobbies
→ 伴侣自己的兴趣爱好，用于在合适话题中自然提及

appearance.heightCm / weightKg
→ 数值类型，单位在字段名中已隐含，Prompt Builder 拼入时加单位文字

appearance.hair / bodyType
→ 面向自然语言描述，直接拼入 Prompt

appearance.additionalTraits
→ 承接后续可扩展描述
```

#### Prompt 构建原则

1. 系统提示词中必须把"伴侣自身设定"与"用户信息"区分成不同区块；
2. `userAddress` 是建议称呼，不强制每句话都使用；
3. Persona 字段缺失时不输出"未知""未设置"等噪音；
4. `systemPrompt` 如存在，拼在结构化 Persona 之后作为补充指令；
5. 不把长篇静态 Persona 重复拼入 Summary 或 Memory。

#### 可观测结果

Demo 中配置：

```txt
用户称呼：鱼头
用户名字：陈大鱼头
伴侣爱好：烘焙、电影
身高：165 cm
发型：黑色长直发
身材：匀称
```

然后确认：

```txt
1. Prompt Preview 可看到完整 Persona 描述，且伴侣设定与用户信息分区清晰；
2. 伴侣回复可自然使用"鱼头"称呼用户；
3. 伴侣可在合适话题中提及自己的兴趣或外貌设定；
4. 未配置字段不出现在 system prompt 中。
```

## 阶段 2：V1.1 契约与兼容边界

### 目标

定义 V1.1 的公共 API、流事件模型和兼容策略，在开始改动工作流实现之前锁定边界。

### 完成标准

- 明确 `executeWorkflow()` 与 `streamWorkflow()` 的职责；
- 明确流事件的类型、顺序、错误语义与完成语义；
- 明确流式工作流中 Tool、Safety、Summary、Memory 的执行位置；
- 明确内部结构化任务（情绪分析、记忆抽取、摘要更新）继续使用 `generate()`；
- 明确旧 API 不删除，旧宿主不因 V1.1 升级而失效；
- 新增 V1.1 stage 文档目录与对应验收标准。

### 02-v1.1-contract.md

#### 双路调用路径

Core 应同时提供两条稳定调用路径：

```ts
core.executeWorkflow(input); // V1.0 保留，返回完整 ChatWorkflowOutput
core.streamWorkflow(input); // V1.1 新增，返回 AsyncIterable<ChatWorkflowStreamEvent>
```

职责约定：

```txt
executeWorkflow
→ 返回完整 ChatWorkflowOutput
→ 适合后台任务、结构化处理、旧宿主兼容、非流式调试

streamWorkflow
→ 返回 AsyncIterable<ChatWorkflowStreamEvent>
→ 适合前台聊天 UI 与实时调试面板
→ 最后必须发送 workflow:finish，携带完整 ChatWorkflowOutput
```

#### 流事件定义

```ts
type ChatWorkflowStreamEvent =
  | { type: "workflow:start"; workflowId: string; timestamp: Date }
  | { type: "step:start"; workflowId: string; step: WorkflowStepName; timestamp: Date }
  | {
      type: "step:end";
      workflowId: string;
      step: WorkflowStepName;
      timestamp: Date;
      summary?: Record<string, unknown>;
    }
  | { type: "text:delta"; workflowId: string; text: string; model?: string }
  | { type: "tool:call"; workflowId: string; call: ModelToolCall }
  | { type: "tool:result"; workflowId: string; result: ToolResult }
  | { type: "workflow:finish"; workflowId: string; output: ChatWorkflowOutput }
  | { type: "workflow:error"; workflowId: string; error: SafeWorkflowError };
```

#### 流式与工具调用边界

V1.1 采用以下策略：

```txt
Persona / Safety / Summary / Memory / Emotion
↓（以上步骤用 generate()，不流式）
工具决策
↓
工具执行（若模型支持且有 toolCalls）
↓
工具二次生成（generate()，不流式）
↓
工具循环结束后
↓
最终自然语言回答使用 stream() 输出 → 发出 text:delta 事件
↓
Output Safety 审计（完整文本后进行）
↓
Summary / Memory 写回
↓
workflow:finish
```

**关键约定：内部结构化任务继续使用 `generate()`**

情绪分析、记忆抽取、摘要更新等内部模型调用必须返回结构化 JSON，继续使用非流式 `generate()`，不改为 `stream()`。"把输出改为流式"只适用于**最终发给用户的自然语言回复**。

约束：

1. V1.1 不实现"已经开始吐字后再插入工具调用"；
2. V1.1 不实现"已经开始吐字后切换 fallback 模型继续拼接"；
3. 流式模型在首个文本 delta 前失败，可按 Model Runtime 的策略重试或 fallback；
4. 已经发送 `text:delta` 后的模型异常，必须发出 `workflow:error`，不得伪装为成功；
5. `workflow:finish` 只在 Output Safety、摘要更新、记忆写回完成或按既有降级策略处理后发送；
6. `CoreObserver` 继续作为旁路观测，不替代 `streamWorkflow()` 的宿主消费协议。

#### 可观测结果

在 Demo 的事件时间线中，至少可看到：

```txt
workflow:start
step:start / step:end
text:delta × N
workflow:finish
```

并能确认：

- 旧 `executeWorkflow()` 仍可调用；
- 新 `streamWorkflow()` 能被独立消费；
- 流结束后可以获得完整 `ChatWorkflowOutput`。

## 阶段 3：模型 Provider 策略与能力声明

### 目标

让 Core 不依赖具体供应商 SDK，让工作流能够通过能力声明决定是否走流式、工具调用等路径，而不是通过 provider 名称写分支。

### 完成标准

- `ChatModel` 增加稳定 `capabilities` 能力声明；
- 宿主配置使用判别联合区分 OpenAI-compatible 与 Ollama；
- `createModel(config)` 根据配置策略创建对应 Adapter；
- Provider 差异不泄漏到 Workflow 业务逻辑；
- 现有 OpenAI-compatible 配置保持兼容；
- Demo 模型面板可显示当前 provider 与支持能力。

### 03-model-provider-strategy.md

#### ChatModel 能力声明

在 Core 抽象层新增：

```ts
interface ModelCapabilities {
  streaming: boolean; // 是否支持 stream()
  toolCalling: boolean; // 是否支持工具调用
  usage: boolean; // 是否返回 token usage
}

interface ChatModel extends CoreProvider {
  readonly capabilities: ModelCapabilities;
  generate(input: GenerateInput): Promise<GenerateOutput>;
  stream(input: GenerateInput): AsyncIterable<GenerateStreamChunk>;
}
```

#### 宿主配置策略

宿主侧模型配置使用判别联合，`provider` 字段作为区分键：

```ts
type ModelConfig = OpenAICompatibleConfig | OllamaConfig;

type OpenAICompatibleConfig = {
  provider: "openai-compatible";
  apiKey: string;
  baseUrl?: string;
  model: string;
  fallbackModel?: string;
  retry?: ModelRetryConfig;
};

type OllamaConfig = {
  provider: "ollama";
  host?: string; // 默认 http://127.0.0.1:11434
  model: string;
  keepAlive?: string;
};
```

`createModel(config: ModelConfig)` 根据 `config.provider` 创建对应实现：

```ts
createModel({ provider: "openai-compatible", ... }) // → OpenAICompatibleModel
createModel({ provider: "ollama", ... })            // → OllamaChatModel（阶段 5 交付）
```

#### Workflow 行为分支原则

Workflow 通过 `capabilities` 而非 provider 名称决定行为：

```ts
// 正确：通过能力声明分支
if (!model.capabilities.toolCalling) {
  // 跳过工具路径，发出可观测事件
}

// 错误：通过 provider 名称分支（禁止）
if (model.meta.id === "model.ollama") { ... }
```

#### 可观测结果

Demo 的模型面板显示：

```txt
provider: openai-compatible | ollama
model: ...
capabilities:
  streaming: true
  toolCalling: true | false
  usage: true | false
```

## 阶段 4：工作流级流式协议与 SimpleChatWorkflow 流式化

### 目标

把"模型级 stream"升级为"Core / Workflow 级 stream"，让宿主可以消费完整聊天生命周期事件，而不只是消费文本片段。

### 完成标准

- `ChatWorkflow` 接口新增 `stream()` 方法；
- `CompanionCore` 提供 `streamWorkflow()`；
- `SimpleChatWorkflow` 实现 `stream()`，能逐步产出 `ChatWorkflowStreamEvent`；
- 伴侣最终回答能真实流式输出；
- 现有 trace、observer、runtime、summary、memory、emotion、tool 结果仍可在 `workflow:finish` 中获取；
- 流失败语义明确，不吞错误；
- `execute()` 行为不受 `stream()` 改造影响（回归验证）。

### 04-streaming-workflow.md

#### 接口扩展

```ts
interface ChatWorkflow extends CoreProvider {
  execute(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): Promise<ChatWorkflowOutput>;

  stream(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

`CompanionCore` 转发：

```ts
core.executeWorkflow(input); // → workflow.execute(input, context)
core.streamWorkflow(input); // → workflow.stream(input, context)
```

#### SimpleChatWorkflow 重构策略（重要）

V1.0 的 `SimpleChatWorkflow` 已达 1527 行。**不能简单复制 `execute()` 的实现来写 `stream()`**，否则两条路径会逐渐漂移，产生难以同步的双重实现。

正确做法分两步：

**步骤一：步骤函数化（先于流式改造提交，独立 review）**

将 `execute()` 中的每个工作流步骤提取为独立的 `async` 函数：

```ts
// 提取示例，实际函数名按项目约定
async function runPersonaStep(...)
async function runSafetyInputStep(...)
async function runSummaryLoadStep(...)
async function runMemoryRecallStep(...)
async function runEmotionStep(...)
async function runToolListStep(...)
async function runToolExecuteStep(...)
async function runSafetyOutputStep(...)
async function runSummarySaveStep(...)
async function runMemoryExtractSaveStep(...)
```

步骤函数化完成后，`execute()` 只是按顺序调用这些函数，行为不变。

**步骤二：实现 `stream()`**

`stream()` 复用步骤函数完成前置准备、Prompt 构建、工具执行、结果收口，只在**最终自然语言生成**环节从 `model.generate()` 切换为 `model.stream()`，并在生成过程中 `yield text:delta` 事件：

```txt
execute() 与 stream() 的分叉点：

共用路径：
  Persona → Safety Input → Summary Load → Memory Recall
  → Emotion → Tool List → Tool Execute（generate()）

execute() 分支：
  → model.generate() → Safety Output → Summary Save → Memory Write
  → return ChatWorkflowOutput

stream() 分支：
  → yield workflow:start / step 事件
  → model.stream() → yield text:delta 事件
  → 流完成后收集完整文本
  → Safety Output → Summary Save → Memory Write
  → yield workflow:finish（含完整 ChatWorkflowOutput）
  → 出错时 yield workflow:error
```

#### 输出安全边界

V1.1 中 Output Safety 保持"完整文本后审计"：

```txt
text:delta 已输出给用户
↓
流完成，得到完整 assistant text
↓
Safety.guardOutput(completeText)
```

若 Output Safety 拒绝：

- 必须发送 `workflow:error`，错误信息表明"输出未通过安全审计"；
- Demo **必须明确标记**该条回复未通过最终审计（不能用 loading 掩盖）；
- 不返回伪造的安全回复；
- 用户已看到的流式文本不能追溯撤回，Demo 应显示审计失败提示。

实时 token 级安全过滤属于后续版本能力，不纳入 V1.1。

#### 可观测结果

Demo 聊天窗口中：

```txt
用户发送消息
↓
伴侣回复逐字出现
↓
流结束后显示 final 状态
↓
侧边调试面板显示：
- workflow trace（step 时序）
- model runtime
- memory recall 结果
- emotion 转变
- tool calls / results（若有）
- summary / memory writeback 结果
```

## 阶段 5：Ollama Adapter

### 目标

增加正式的 Ollama `ChatModel` Adapter，使本地模型可注入 V1.1 Core，而不是通过 OpenAI-compatible 接口模拟。

### 完成标准

- 新增独立 `packages/model-ollama` package；
- 使用 `ollama` npm 包实现 `ChatModel`；
- 支持 `generate()` 与 `stream()`；
- `capabilities` 正确声明该 Adapter 的能力；
- 支持宿主配置 host、model、keepAlive；
- 对工具调用能力做明确映射或显式能力降级；
- OpenAI-compatible 与 Ollama 使用同一套 Core / Workflow API；
- Demo 可切换两个 Provider。

### 05-ollama-model-adapter.md

#### 包边界

```txt
packages/
├── ai-core/
│   ├── ChatModel 抽象（含 capabilities）
│   ├── Workflow
│   └── 流协议
│
├── model-ollama/
│   ├── OllamaChatModel（实现 ChatModel 接口）
│   ├── OllamaConfig
│   └── Ollama message / tool call 映射
│
└── memory-postgres/
    └── PostgresMemoryProvider（V1.1 Embedding 仍用 OpenAI，不变）
```

约束：

```txt
- ollama npm 依赖不得进入 ai-core
- ai-core 不得读取 OLLAMA_HOST / OLLAMA_MODEL
- 宿主负责读取环境变量或表单配置，再创建 OllamaChatModel
- Workflow 不得直接判断 provider 名称，只通过 ChatModel.capabilities 行为分支
```

#### Embedding Provider 边界说明

V1.1 中切换到 Ollama **模型**时，记忆系统的 Embedding 向量化仍由宿主注入的 `EmbeddingProvider`（通常是 `OpenAIEmbeddingProvider`）负责，与聊天模型的 provider 选择无关。Ollama Embedding Provider 不属于 V1.1 范围，Demo 中应在模型切换说明里注明此约束。

#### 运行时语义

```txt
OpenAI-compatible

Ollama
→ 先实现单模型本地调用与流式输出
→ runtime 中明确 provider、model、attempts
→ 若不支持 fallback，不虚构 fallback 状态
→ capabilities.toolCalling 根据模型实际能力声明，工作流按此分支
```

#### 工具调用边界

Ollama 模型与模型版本对 tool calling 的支持可能不同。V1.1 必须：

1. 在 `capabilities.toolCalling` 中明确声明；
2. 若当前模型不支持工具调用，工作流必须跳过工具路径并发送可观测事件或 trace 标记；
3. 不得让"不支持 tool calling"变成难以定位的 prompt 或解析异常；
4. 不要求所有 Ollama 模型在 V1.1 中都通过工具调用验收。

## V1.1 架构演进结果

V1.1 完成后，目标调用路径为：

```txt
宿主应用 / Debug Workbench
  ↓
读取环境变量或页面配置
  ↓
createModel(ModelConfig)          // config.provider 决定实现
  ↓
OpenAICompatibleModel | OllamaChatModel
  ↓
createCompanionCore({ model, persona, memory, emotion, tools, ... })
  ↓
core.streamWorkflow(input)
  ↓
AsyncIterable<ChatWorkflowStreamEvent>
  ↓
聊天 UI（text:delta 逐字展示）+ Workflow Debug Timeline（step / finish 事件）
```

Core 内部目标编排为：

```txt
Persona:load
↓
Safety:input（generate，内部）
↓
Summary:load（generate，内部）
↓
Memory:recall（generate，内部）
↓
Emotion:analyze / transition（generate，内部）
↓
Tool:list / Tool:execute（generate，内部）
↓
Final Response → model.stream() → text:delta × N（用户可见流式输出）
↓
Safety:output（完整文本后审计）
↓
Summary:save
↓
Memory:extract / Memory:save（generate，内部）
↓
workflow:finish（含完整 ChatWorkflowOutput）
```

## V1.1 关键设计原则

1. `streamWorkflow()` 是新增公开 API，不替换或删除 `executeWorkflow()`；
2. 模型级流与工作流级流必须区分，宿主应消费工作流事件而不是直接消费模型文本；
3. **最终用户可见回复才流式化**，内部结构化任务（情绪、记忆、摘要）继续使用 `generate()`；
4. 流式工具调用采用"先完成工具循环（generate）再流式最终回答（stream）"的稳定策略；
5. Persona 是 Core 配置，不依赖用户系统；
6. `userAddress` 是伴侣对用户的称呼，而不是未来用户体系中的账号昵称；
7. 外部 SDK Adapter 必须独立 package，`ai-core` 保持纯 SDK；
8. Workflow 不通过 provider 名称写分支，只通过 `ModelCapabilities` 决定行为；
9. 所有模型配置由宿主读取和注入，`ai-core` 不读取环境变量；
10. Ollama Embedding Provider 不属于 V1.1，Embedding 仍由宿主独立注入；
11. Demo 是长期保留的调试工作台，不是一次性临时页面；
12. 任何流式失败都必须可观测、可定位，不得用伪成功掩盖；
13. Output Safety 拒绝时 Demo 必须明确标注，不能以 loading 状态掩盖；
14. `SimpleChatWorkflow` 流式改造前必须先完成步骤函数化重构，独立提交并 review；
15. 每个阶段完成后必须有可复现的人工验证结果与 review 归档。
