# AI Companion Core V1.2 实施方案

> 版本目标：在 V1.0 / V1.1 已完成的 Core SDK、模型策略、流式 Workflow、Tool Planning、Ollama Adapter 与 Debug Workbench 基础上，完成「可替换的 Web Search 工具接入」与「基于 AI SDK UI 的 Demo 聊天体验升级」。
>
> V1.2 只包含两个阶段：
>
> 1. Web Search Tool 实施；
> 2. Demo UI 升级与项目文档收口。
>
> 本版本仍只面向本地开发、Core / SDK 验证与 Debug Workbench，不引入正式产品 UI、用户系统、鉴权、生产部署、商业化或多 Agent。

## V1.2 核心目标

将当前只能调用本地时间、记忆、情绪等内部工具的 Companion，升级为：

```txt
用户提出需要时效信息的问题
↓
（对话 webSearchEnabled=true 且基础设施可用）
↓
Tool Planning
↓
web_search Tool
↓
外部搜索 Provider
↓
标准化搜索结果与来源
↓
Final Response
↓
AI SDK UI 消息流
├── 流式文本
├── 搜索状态
├── 工具状态
└── 可点击来源卡片
```

V1.2 完成后，Demo 宿主应支持：

1. 用户可在**当前对话**决定是否启用 Web Search（业务侧开关）；仅当对话开关打开且基础设施可用时，模型才可能在 Tool Planning 中选择 `web_search`；
2. 模型在适当场景选择 `web_search`，例如新闻、天气、价格、产品动态、近期事件、公开资料核实；
3. 搜索结果以统一结构进入最终回答，而不是将供应商原始响应直接塞给模型；
4. 伴侣最终回答能够基于搜索结果生成，并在 UI 中展示可点击来源；
5. 前端聊天改用 AI SDK UI 的 `useChat`、`UIMessage` 与 UIMessage Stream 协议管理流式消息状态；
6. Workflow 状态、工具执行、搜索查询与最终来源仍可在 Debug Workbench 中查看；
7. 不破坏现有 `CompanionCore`、`ToolRegistry`、`streamWorkflow()`、Memory scope、会话持久化与模型 Adapter 边界。

## 关键架构决策

### 1. Web Search 必须是现有 Tool 系统的一个外部 Adapter

V1.0 已经有稳定的 `ToolProvider` / `ToolRegistry` 契约：Workflow 列出工具、Tool Planning 决定是否调用、Registry 执行工具、`ToolResult` 回填到最终回答上下文。

因此 V1.2 不新增第二套 Agent Tool 体系，不在 Workflow 中特殊硬编码“搜索逻辑”。

目标形态：

```txt
apps/model-runtime-demo
  ├── 读取 TAVILY_API_KEY / WEB_SEARCH_*（基础设施层）
  ├── 读取 conversation.webSearchEnabled（业务层）
  ├── 条件满足时创建 TavilyWebSearchToolAdapter
  └── 条件满足时 register(web_search)

packages/tool-web-search
  ├── WebSearchClient 抽象
  ├── WebSearchResult 标准结构
  ├── TavilyWebSearchClient 实现
  └── createWebSearchTool(...) 工厂

packages/ai-core
  └── 只通过 ToolRegistry.list / execute 消费 web_search
```

`ai-core` 不导入 Tavily SDK、不读取 `TAVILY_API_KEY`、不理解 `search_depth`、不依赖 URL 搜索 API。

### 2. Tavily 是 V1.2 的唯一 Provider，但不是 Core 的永久绑定

V1.2 选择 Tavily 作为首个 Provider，原因是其 Search API 直接返回标题、URL、摘要、相关性分数，并支持新闻/通用主题、时效范围、域名限制等 Agent 常用参数。

但 `packages/tool-web-search` 内部必须先建立供应商无关的 `WebSearchClient` 与标准结果结构：

```ts
export interface WebSearchClient {
  search(input: WebSearchRequest): Promise<WebSearchResponse>;
}
```

后续接 Exa、Serper、Brave、Bing 或企业内部搜索，只替换或新增 `WebSearchClient` 实现；`web_search` Tool Definition、Workflow 与 Demo 来源渲染不应被迫修改。

### 3. 搜索数据不应被误写为用户长期记忆

Web Search 返回的是外部、可变、带时效性的公开资料，不是用户事实、偏好、关系事件或长期经历。

因此：

```txt
搜索结果
├── 作为本轮 Final Response 的临时上下文
├── 作为本轮 Tool Result / Source 数据供 UI 展示
├── 可保留在会话消息与 Workflow Run 调试记录中
└── 不得作为 Memory Extractor 的候选输入自动保存
```

Memory Extractor 仍只从用户陈述、关系上下文与明确可持久化的对话事实中抽取记忆。

V1.2 必须落实为可执行机制，不能只写在文档里。当前 `ModelMemoryExtractor` 会接收完整 `assistantMessage`，其中可能包含基于搜索生成的事实，因此至少采用以下组合：

```txt
1. workflow 层：若本轮存在成功的 web_search Tool Result，向 Memory Extractor 传入
   `externalContextUsed: true` 或 `excludedToolNames: ["web_search"]`
2. extractor prompt：明确「不得将本轮 web_search 引用的外部公开信息写入长期记忆」
3. 可选：对 assistantMessage 做来源事实剥离（V1.2 不强制，但不得仅靠模型自觉）
```

实现落点优先在 **宿主或 workflow 传入的 `MemoryExtractionInput` 扩展字段** + **extractor system prompt 补充**，不要求为单个 tool 修改 `ai-core` 的 Memory 存储契约。

### 4. Web Search 采用「基础设施开关 + 对话业务开关」双层门控

Web Search 是否可用，由两层独立判断：

```txt
基础设施层（宿主 env / 部署）
├── TAVILY_API_KEY 存在
├── WEB_SEARCH_ENABLED !== false（可选全局 kill switch）
└── 当前实际模型 profile.capabilities.toolCalling === true

业务层（用户 / 当前对话）
└── debug_conversations.web_search_enabled === true
    → 本轮才向 ToolRegistry 注册 web_search
```

语义约定：

```txt
- env / key：开发者控制「系统有没有搜索能力」
- conversation.webSearchEnabled：用户控制「这场对话要不要用搜索」
- 默认 false：新对话默认关闭，由用户主动开启，避免误触产生外部请求与费用
- ai-core 不感知该开关；宿主在 createConversationRuntime / createDemoTools 时决定是否 register
- 关闭时不注册 web_search，而不是注册 Disabled Tool 让 Planner 看到但执行失败
- Demo Runtime 面板展示不可用原因：user_disabled | infra_unavailable | model_unsupported | enabled
```

对话开关持久化：

```sql
ALTER TABLE debug_conversations
ADD COLUMN IF NOT EXISTS web_search_enabled BOOLEAN NOT NULL DEFAULT false;
```

API：

```txt
PATCH /api/conversations/[id]  { "webSearchEnabled": true }
GET  /api/conversations/[id]   → 返回 webSearchEnabled
```

发送消息以对话持久化值为准，不要求每轮请求重复携带开关；后续若需要「仅本条消息搜索」，再扩展 message 级覆盖。

### 5. AI SDK UI 只替换宿主流式消费层，不替换 Core

V1.1 已冻结两层边界：

```txt
Core Stream Event
→ 含 Date / raw / 调试字段的内部事件

Wire Event
→ 可 JSON 序列化的宿主传输事件
```

V1.2 再新增第三层：

```txt
AI SDK UIMessage Stream
→ 用于 useChat / UIMessage / source / data parts 的 UI 协议
```

最终关系：

```txt
CompanionCore.streamWorkflow()
  ↓
ChatWorkflowStreamEvent
  ↓
Demo Host Event Bridge
  ↓
AI SDK UIMessage Stream
  ↓
useChat<MyUIMessage>()
  ↓
Chat UI / Source Cards / Debug Panels
```

这是一层宿主适配，不能反向污染 `packages/ai-core`。

协议迁移策略（相对 V1.1 NDJSON Wire Event）：

```txt
对外主通道（浏览器 useChat）
→ /api/conversations/[id]/messages 返回 AI SDK UIMessage Stream

内部调试 / 契约验证
→ 仍可从 Core Event 显式映射出 Wire Event 或精简 JSON，供 Debug Drawer 与 verify 脚本使用
→ verify:stream-contract 在 V1.2 扩展为「Core Event → UIMessage Stream」映射校验；Wire 映射可保留为内部辅助，不阻塞 UI 迁移

遗留入口
→ 冻结或移除 chat-panel.tsx 与 /api/chat；Stage 8 主路径以 ConversationWorkspace 为准
```

### 6. UIMessage 历史不是 Core 的唯一事实来源

AI SDK UI 的 `UIMessage` 包含 text、source、data part 等渲染状态；Core 只需要自身稳定的 `ChatMessage[]` 和持久化会话数据。

因此：

```txt
Conversation Store / 数据库
→ 会话与消息的最终事实来源

UIMessage
→ 当前页面的流式渲染模型

Host Mapper
→ 只把 user / assistant 的 text part 转换为 Core ChatMessage
→ source / data / transient part 不得被误传为 Core 对话历史
```

不能把完整 `UIMessage[]` 不加转换地塞回 `core.streamWorkflow()`。

来源数据刷新后的持久化策略（V1.2 明确选型）：

```txt
消息正文（user / assistant text）
→ 继续写入 debug_messages.content，作为 Core history 与聊天主文本来源

搜索来源（source parts）
→ 写入 debug_workflow_runs 的 run 记录 JSON（与 Tool Result / Trace 同源）
→ 页面刷新后：聊天区恢复文本；来源卡从「当前选中 run」或「assistant 消息关联 run」恢复渲染
→ V1.2 不扩展 debug_messages 表存 UIMessage parts；避免 message / UIMessage 双写
```

### 7. `stop()` 仅为客户端中止，不承诺服务端续传

与 V1.1 已知约束一致：

```txt
- useChat.stop() 中止浏览器端 fetch / 流消费
- 服务端 workflow 可能仍继续执行直至自然结束；V1.2 不实现服务端 abort token
- 中止后持久化：若 assistant 尚未 completeRun，标为 aborted / partial；不得伪装成「断线续传已实现」
- UI 明确区分 stopped / completed / failed
```

## 总体阶段规划

```txt
阶段 1：Web Search Tool Adapter 与搜索闭环实施
阶段 2：AI SDK UI Demo 升级与项目文档收口
```

阶段顺序不得调整：

```txt
先完成 Tool Adapter、来源结构、错误语义与 Core 真实搜索闭环
↓
再将稳定结果桥接到 AI SDK UI 并重做 Demo 视觉与文档
```

原因：如果先做 UI，前端会被迫猜测搜索状态、来源格式与错误结构；最终容易出现 UI 先写死、后端被迫迎合的反向耦合。

阶段 2 建议里程碑（可在 `.requirements/stages/v1.2/` 拆为子文档，但版本仍计为 1 个阶段）：

```txt
2a. Core Event → UIMessage Stream 桥接 + 持久化 / stop 语义
2b. useChat 聊天 UI、来源卡、对话 Web Search 开关
2c. Debug Drawer 保留 + 文档 / verify 契约收口
```

## 阶段 1：Web Search Tool Adapter 与搜索闭环实施

### 目标

通过现有 `ToolRegistry` 注入一个可替换的 `web_search` 工具，使 Tool Planning 能在需要时调用外部搜索，并把标准化结果、来源与执行状态带入最终回答、Workflow Trace 和宿主调试数据。

### 完成标准

- 新增独立包 `packages/tool-web-search`；
- `packages/ai-core` 不新增 Tavily 依赖、不读取环境变量；
- 宿主从 `TAVILY_API_KEY` 创建 Tavily 实现，并在条件满足时注册 `web_search`；
- `debug_conversations.web_search_enabled` 持久化对话级业务开关，默认 `false`；
- `PATCH /api/conversations/[id]` 可更新 `webSearchEnabled`；
- 仅当基础设施可用、模型支持 toolCalling、且对话开关为 `true` 时，模型才可能在 Tool Planning 中看到 `web_search`；
- `web_search` 执行成功后，最终回答使用搜索结果；
- Tool Result 中包含可序列化的标准化来源；
- 搜索失败时返回结构化 `ToolResult` 错误，不让原始异常穿透到用户界面；
- 搜索能力不可用或当前模型不支持 Tool Calling 时，工作流按既有降级语义继续；
- 搜索结果不会自动写入长期 Memory（含 extractor 输入约束或 prompt 防护）；
- Demo Runtime 可观察 Web Search 状态（enabled / user_disabled / infra_unavailable / model_unsupported）、query、Provider、耗时、结果数、来源与失败原因；
- 新增阶段验证脚本或人工验证路径，证明真实搜索与失败降级均可复现。

职责约束：

```txt
packages/tool-web-search
├── 可以依赖 Tavily SDK 或 HTTP Client
├── 可以定义 Web Search 标准结果
├── 可以实现 ToolHandler
├── 不能依赖 Next.js / React / AI SDK UI
├── 不读取 process.env
└── 不连接 PostgreSQL 或 Memory Provider
```

#### 2. 统一搜索数据结构

不要把供应商原始字段直接作为 Tool Result 主体；必须先归一化。

```ts
export type WebSearchTopic = "general" | "news";
export type WebSearchTimeRange = "day" | "week" | "month" | "year";

export interface WebSearchRequest {
  query: string;
  topic?: WebSearchTopic;
  timeRange?: WebSearchTimeRange;
  includeDomains?: string[];
  excludeDomains?: string[];
}

export interface WebSearchSource {
  id: string;
  title: string;
  url: string;
  snippet: string;
  publishedAt?: string;
  score?: number;
  faviconUrl?: string;
}

export interface WebSearchResponse {
  query: string;
  sources: WebSearchSource[];
  provider: string;
  durationMs?: number;
  metadata?: Record<string, unknown>;
}
```

硬性约束：

```txt
- url、title、snippet 是 V1.2 必须字段；
- 不返回原始 HTML、Markdown 全文、raw_content；
- 不将 Tavily answer 作为可信最终回答直接展示；
- 搜索 Provider 的原始 response 仅可进入受限 debug 字段，不得进入 Prompt 或 UIMessage 持久化数据；
- URL 必须是 http / https；非法 URL 丢弃；
- snippet 必须截断，避免单次 Tool Result 无限制膨胀上下文；
- source 总数由宿主固定上限控制，V1.2 默认不超过 5 条。
```

#### 3. `web_search` Tool Definition

工具定义必须面向模型，但成本、深度和供应商参数由宿主控制。

```ts
const webSearchDefinition: ToolDefinition = {
  name: "web_search",
  description:
    "搜索公开网页以获取近期、实时或需要核实的信息。适合新闻、当前事件、价格、天气、产品动态、公开资料核实。不要用于用户个人记忆、纯聊天、主观陪伴或可由已有上下文回答的问题。",
  parameters: {
    type: "object",
    properties: {
      query: {
        type: "string",
        description: "简洁、可检索的搜索关键词或问题。",
      },
      topic: {
        type: "string",
        enum: ["general", "news"],
      },
      timeRange: {
        type: "string",
        enum: ["day", "week", "month", "year"],
      },
      includeDomains: {
        type: "array",
        items: { type: "string" },
      },
    },
    required: ["query"],
    additionalProperties: false,
  },
  metadata: {
    tags: ["web", "search", "external", "time-sensitive"],
  },
};
```

说明：`searchDepth`、`maxResults`、`includeRawContent`、`autoParameters`、请求超时、重试次数等不得由模型自由决定，应由宿主构造 `TavilyWebSearchClient` 时固定。

#### 4. Tavily 实现与宿主配置

V1.2 首个实现为 `TavilyWebSearchClient`。

宿主新增环境变量：

```env
TAVILY_API_KEY=
```

可选宿主配置：

```env
WEB_SEARCH_ENABLED=true
WEB_SEARCH_TIMEOUT_MS=8000
WEB_SEARCH_MAX_RESULTS=5
WEB_SEARCH_TOPIC=general
WEB_SEARCH_SEARCH_DEPTH=basic
```

约束：

```txt
- `TAVILY_API_KEY` 只在 Demo Server Route / Server-only Factory 中读取；
- 浏览器端不得接触 API Key；
- 基础设施不可用（缺 key / WEB_SEARCH_ENABLED=false）时不注册 web_search；
- 对话 `webSearchEnabled=false` 时不注册 web_search；
- 不可用原因由 Demo Runtime 面板展示，不依赖 core.inspect() 的 tools.meta（其仅返回 Registry meta）；
- V1.2 默认只实现 Tavily，不实现跨 Provider fallback；
- 429、网络超时、5xx 可在 Adapter 内做有限重试；
- 4xx 参数错误、401 / 403 认证错误不得盲目重试；
- 所有异常最终必须映射为 `ToolResult.ok = false` 与稳定错误语义。
```

错误码策略（不扩展 `ai-core` 的 `ToolExecutionErrorCode` union）：

```txt
ToolResult.error.code 保持既有三类之一，优先 TOOL_EXECUTION_FAILED
ToolResult.error.metadata 或 metadata 承载领域码，例如：
  { domain: "web_search", code: "WEB_SEARCH_TIMEOUT" }

建议 domain 码：
WEB_SEARCH_DISABLED
WEB_SEARCH_INVALID_QUERY
WEB_SEARCH_TIMEOUT
WEB_SEARCH_RATE_LIMITED
WEB_SEARCH_UNAUTHORIZED
WEB_SEARCH_PROVIDER_ERROR
WEB_SEARCH_NO_RESULTS
```

宿主 UI / Debug 按 `metadata.domain + metadata.code` 分支，不得依赖自由文本 `message`。

#### 5. Tool Result、Prompt 与来源约定

执行成功时：

```ts
const result: ToolResult = {
  toolCallId: input.call.id,
  name: "web_search",
  ok: true,
  result: {
    query: response.query,
    sources: response.sources,
  },
  metadata: {
    provider: response.provider,
    durationMs: response.durationMs,
    sourceCount: response.sources.length,
    // sources 副本仅供 UI / Debug；formatToolResultForModel 只序列化 result 字段
  },
};
```

执行失败时：

```ts
const result: ToolResult = {
  toolCallId: input.call.id,
  name: "web_search",
  ok: false,
  result: null,
  error: {
    code: "TOOL_EXECUTION_FAILED",
    message: "Web Search 请求超时",
  },
  metadata: {
    provider: "tavily",
    domain: "web_search",
    code: "WEB_SEARCH_TIMEOUT",
  },
};
```

引用与来源约束的代码落点（当前无独立 Final Response Prompt Builder）：

```txt
1. tool follow-up 上下文：formatToolResultForModel(result) 之前，对 web_search 成功结果附加 framing
2. framing 须包含：
   - 搜索结果是外部参考资料，不是系统事实
   - 回答只能基于 sources 概括，不得捏造来源未包含的具体事实
   - 引用外部事实时使用 [1]、[2]，编号按 sources 顺序
   - 搜索失败或无结果时坦诚说明，不得伪造
   - 不得把搜索结果改写为用户长期偏好、关系记忆或事实记忆
3. 引用编号规则也可写入 workflow-final-response 组装 final messages 时的 system 补充段
4. 不得改 persona-prompt-builder 的全局伴侣人设；搜索引用规则属于本轮 tool context
```

> 注意：模型生成的 `[1]` 文本只是一种可读提示；真正可点击来源以宿主接收到的标准化 `sources` 为准，UI 不得通过解析模型文本反推 URL。

#### 6. Tool Planning 与模型能力边界

V1.1 已经把 Tool Planning 与 Final Response 分离。V1.2 必须沿用该设计：

```txt
Tool Planning
├── 仅产出 no_tool / tool_calls
├── 可选择 web_search
└── 不生成面向用户的最终自然语言回答

Tool Execute
├── 执行 Tavily 搜索
├── 标准化结果
└── 发出 tool:call / tool:result 事件

Final Response
├── 接收标准化搜索来源
├── generate 或 stream 最终回答
└── 返回自然语言与引用标记
```

模型能力约束：

```txt
- 条件注册发生在宿主 createDemoTools / createConversationRuntime，不在 ai-core Workflow 内；
- 当前实际运行模型不支持 toolCalling 时，不注册 web_search；
- 对话 webSearchEnabled=false 时，不注册 web_search；
- primary → fallback 后必须按 V1.1 既有逻辑重新评估能力；
- 默认声明不支持 Tool Calling 的 Ollama 配置，不应出现“模型尝试调用 web_search 后失败”；
- Demo 顶栏 / Runtime 必须展示 Web Search 状态与不可用原因。
```

#### 7. 对话级 Web Search 开关（业务侧）

```ts
function resolveWebSearchRegistration(input: {
  env: NodeJS.ProcessEnv;
  conversationWebSearchEnabled: boolean;
  modelProfile: ModelProfile;
}): "register" | "user_disabled" | "infra_unavailable" | "model_unsupported" {

  if (!input.conversationWebSearchEnabled) return "user_disabled";
  if (!input.modelProfile.capabilities.toolCalling) return "model_unsupported";

}
```

#### 2. UIMessage 类型与 Data Parts

在 Demo 内新增专属 UIMessage 类型，例如：

```ts
export type DemoChatMessage = UIMessage<
  DemoMessageMetadata,
  {
    workflow: DemoWorkflowData;
    tool: DemoToolData;
    webSearch: DemoWebSearchData;
    runtime: DemoRuntimeData;
  }
>;
```

用途约定：

```txt
text part
→ 用户与伴侣的可见自然语言消息

source part
→ Web Search 返回的 URL、标题与来源标识
→ 可进入 assistant UIMessage，用于聊天记录中的引用卡片

transient data-workflow
→ 当前步骤、加载状态、错误提示
→ 仅用来驱动实时 UI，不进入消息持久化

data-tool / data-webSearch
→ 本轮需要在聊天记录内保留的精简工具摘要
→ 不携带 raw provider response

data-runtime
→ 最终模型、fallback、耗时等精简运行信息
→ 不包含 key、headers、原始异常堆栈
```

#### 3. Core Event → UIMessage Stream Bridge

新增 Demo Host 层桥接模块，例如：

```txt
apps/model-runtime-demo/app/lib/ai-sdk-ui/
├── demo-ui-message.ts
├── core-event-to-ui-message-stream.ts
├── core-history-mapper.ts
└── conversation-ui-message-mapper.ts
```

Server Route 负责：

```txt
1. 读取请求与会话上下文（含 conversation.webSearchEnabled）；
2. 按双层门控创建 CompanionCore 与条件注册的 web_search Tool；
3. 调用 core.streamWorkflow(input)；
4. 消费 ChatWorkflowStreamEvent；
5. 使用 createUIMessageStream / createUIMessageStreamResponse 生成 AI SDK UI 协议；
6. 将最终 workflow output、会话持久化结果与精简 Debug 数据写入 UIMessage data parts；
7. 在所有后置写回完成后结束流。
```

事件映射建议：

```txt
workflow:start
→ transient data-workflow { status: "started" }

step:start / step:end
→ transient data-workflow { step, status, summary? }

text:delta
→ UIMessage text-start / text-delta / text-end

tool:call
→ transient data-tool { status: "running", name, query? }

tool:result (web_search)
→ data-webSearch { status, query, provider, sourceCount }
→ 每个 WebSearchSource 映射一个 source part

tool:result (其他工具)
→ data-tool { status, name, ok }

workflow:finish
→ data-runtime / data-workflow 最终状态
→ 写入会话持久化成功后关闭流

workflow:error
→ UIMessage error 语义 + transient data-workflow error
```

硬性约束：

```txt
- Core Event 与 AI SDK UI 协议之间必须有显式 adapter；
- 不允许 Route 直接把 Core Event JSON 原样塞进 UIMessage；
- 不允许 UIMessage raw data 回传给 ai-core；
- 不允许把 API Key、模型 raw response、错误 stack 或完整搜索原始响应写入 UIMessage；
- Source URL 仅来自标准化 WebSearchSource；
- 正常 `workflow:finish` 只能在消息 / workflow 后置持久化完成后发送。
```

#### 4. `useChat` 与会话持久化边界

AI SDK UI 文档中的 `useChat` 可管理消息、流式状态、错误与停止操作；但当前 Demo 已有会话 / 消息持久化机制，不能把两者做成两个相互竞争的真相来源。

必须采取：

```txt
持久化 Conversation / Message Store
→ 历史事实来源

useChat messages
→ 当前页面的 UI 渲染状态

页面初次加载
→ 从 Conversation API 加载持久化消息
→ 映射为 DemoChatMessage

发送消息
→ useChat / Transport 发送当前用户 text
→ Server Route 内构造 Core ChatMessage history
→ Workflow 完成后持久化 canonical message
→ UIMessage 接收流式 assistant message
```

历史映射规则：

```txt
- user / assistant 文本映射为 Core ChatMessage；
- UIMessage 的 source、tool、runtime、workflow data parts 不得传入 Core History；
- Core 仍由 `history`、Summary、Memory、Persona 组装上下文；
- 页面刷新后优先从持久化记录恢复，而不是依赖 useChat 内存状态；
- assistant 文本来自 `debug_messages`；source parts 来自关联 workflow run 的持久化 JSON；
- V1.2 不实现 AI SDK UI Resume Streams。
```

## V1.2 实施后的边界冻结

V1.2 完成后，后续需求必须默认遵守：

```txt
1. 新外部能力优先通过 Tool Registry 接入，不在 Workflow 硬编码分支；
2. 新搜索 Provider 优先实现 WebSearchClient，不修改 ai-core；
3. 外部检索资料不是用户长期 Memory；
4. Web Search 采用基础设施开关 + 对话业务开关双层门控，业务开关不进 ai-core；
5. Core Stream Event、Wire Event、UIMessage Stream 是三层不同协议；
6. useChat 管理 UI 状态，不替代 Conversation Store 或 CompanionCore；
7. 来源链接只来自标准化 Tool Result，不来自模型文本解析；
8. API Key 只停留在 Server Host，绝不进入浏览器、UIMessage 或 Debug raw payload；
9. Demo 的视觉升级不等于正式产品 UI 架构已经确定。
```
