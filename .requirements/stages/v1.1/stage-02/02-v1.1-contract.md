# AI Companion Core V1.1 - 阶段 2：V1.1 契约、事件、Wire 协议与兼容边界实施文档

## 一、阶段目标

在改造 `SimpleChatWorkflow`、接入模型 Provider 策略、实现 Ollama Adapter 与升级 Demo 网络层之前，先冻结 V1.1 的公共契约。

本阶段交付的是：

1. Core 的双路工作流调用边界；
2. Core 内部流事件契约；
3. Core Event 到网络 Wire Event 的序列化边界；
4. 流事件的顺序、完成、错误与部分输出语义；
5. 旧宿主与旧自定义 Workflow 的兼容策略；
6. V1.1 后续阶段必须遵守的职责约束。

本阶段**不实现真实流式聊天**、不重构 `SimpleChatWorkflow`、不接入 Ollama、不修改模型 Provider 策略、不修改 Demo 的聊天网络请求。

> 本阶段的原则是：先定义稳定的“语言”，后续阶段才能在不反复改接口的前提下实现流式工作流与宿主消费层。

## 五、双路工作流调用契约

### 5.1 CompanionCore 公共 API

V1.1 必须保留既有非流式入口，并新增流式入口：

```ts
interface CompanionCore {
  executeWorkflow(input: ChatWorkflowInput): Promise<ChatWorkflowOutput>;

  streamWorkflow(input: ChatWorkflowInput): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

语义：

```txt
executeWorkflow()
→ 返回完整 ChatWorkflowOutput。
→ 继续服务 V1.0 宿主、后台任务、结构化调用、非流式调试。
→ 不得因 V1.1 引入 stream 而改变现有成功 / 降级 / 错误语义。

streamWorkflow()
→ 返回 Core 内部事件流。
→ 面向聊天 UI、实时 Debug Workbench 与未来任意宿主。
→ 不直接返回 HTTP Response、ReadableStream 或 NDJSON 字符串。
```

### 5.2 不允许用 streamWorkflow 取代 executeWorkflow

以下做法禁止：

```ts
// 禁止：executeWorkflow 内部通过消费 streamWorkflow 拼回结果，
// 以此替换既有 V1.0 执行路径。
async executeWorkflow(input) {
  for await (const event of this.streamWorkflow(input)) {
    // ...
  }
}
```

原因：

- V1.0 的 `executeWorkflow()` 已有稳定行为与调试语义；
- V1.1 阶段 4 的目标是抽取共享步骤函数，而不是让一条路径伪装为另一条路径；
- 执行与流式输出应共享步骤能力，但各自保留清晰的编排边界。

阶段 4 之后允许两条路径复用相同的内部步骤函数；是否由某个内部执行计划驱动两条路径，由阶段 4 / 5 决定，但不得改变公开 API 语义。

### 5.3 ChatWorkflow 的兼容扩展

为避免已有自定义 Workflow 因新增方法而发生 TypeScript 破坏性变更，`stream` 在本阶段必须是可选能力：

```ts
interface ChatWorkflow extends CoreProvider {
  execute(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): Promise<ChatWorkflowOutput>;

  stream?(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

兼容策略：

```txt
旧自定义 Workflow
→ 只实现 execute() 仍可通过 typecheck。
→ 旧宿主继续调用 executeWorkflow() 时行为不变。

宿主调用 streamWorkflow()
→ Workflow 已实现 stream()：CompanionCore 委托其输出事件。
→ Workflow 未实现 stream()：由 CompanionCore 统一兜底（不得由各 Workflow 自行实现不一致语义）；不得伪造逐字输出；发出 workflow:start 后，发出 workflow:error，错误码为 workflow_stream_not_supported，然后结束。

SimpleChatWorkflow
→ 阶段 5 必须实现 stream()，成为 V1.1 默认的真实流式 Workflow。
```

### 5.4 流式执行不支持取消与恢复

V1.1 不在 `streamWorkflow()` 中加入 `AbortSignal`、续传 cursor、断线恢复或 token 重放。

原因：这些能力会影响 Provider 调用取消、会话写回幂等、NDJSON 重连与前端状态机，应在后续版本单独设计。

## 六、Core 流事件契约

### 6.0 CoreObserver 与 Stream Event 的关系

V1.0 已有 `CoreObserver`，其中包含 `workflow:start`、`workflow:step`、`workflow:end`、`workflow:error` 等事件类型。V1.1 新增的 `ChatWorkflowStreamEvent` 在命名上部分重叠，但职责不同：

```txt
CoreObserver
→ 旁路可观测通道；宿主可选订阅，用于 Debug / 日志 / 持久化。
→ 不替代 streamWorkflow() 的宿主消费协议。
→ workflow:end 表示 Observer 视角下的工作流结束。

ChatWorkflowStreamEvent
→ streamWorkflow() 的主协议；聊天 UI 与 NDJSON 消费层必须依赖此契约。
→ workflow:finish 表示流式协议视角下的成功/降级终止（携带完整 ChatWorkflowOutput）。
→ workflow:error 表示流式协议视角下的失败终止。

易混淆点
→ workflow:end（Observer）≠ workflow:finish（Stream）。
→ Observer 的 workflow:step 与 Stream 的 step:start / step:end 是不同事件，不得共用同一套 UI handler。
```

约束：

```txt
- SimpleChatWorkflow 实现 stream() 时，仍应继续 emit CoreObserver 事件，保持 V1.0 调试能力；
- Demo 的 Workflow Debug Timeline 以 ChatWorkflowStreamEvent 为主时间线；
- CoreObserver 事件可作为补充调试信息，但不得与 Stream 事件混为同一 type 分发表。
```

### 6.1 事件类型

新增或独立导出以下类型：

```ts
export type ChatWorkflowStreamEvent =
  | WorkflowStartStreamEvent
  | WorkflowStepStartStreamEvent
  | WorkflowStepEndStreamEvent
  | WorkflowTextDeltaStreamEvent
  | WorkflowToolCallStreamEvent
  | WorkflowToolResultStreamEvent
  | WorkflowFinishStreamEvent
  | WorkflowErrorStreamEvent;

export interface WorkflowStartStreamEvent {
  type: "workflow:start";
  workflowId: string;
  timestamp: Date;
}

export interface WorkflowStepStartStreamEvent {
  type: "step:start";
  workflowId: string;
  step: WorkflowStepName;
  timestamp: Date;
}

export interface WorkflowStepEndStreamEvent {
  type: "step:end";
  workflowId: string;
  step: WorkflowStepName;
  timestamp: Date;
  /** 与 WorkflowStepTrace.status 对齐，禁止仅通过 summary 隐式表达。 */
  status: WorkflowStepStatus;
  summary?: Record<string, unknown>;
}

export interface WorkflowTextDeltaStreamEvent {
  type: "text:delta";
  workflowId: string;
  text: string;
  model?: string;
}

export interface WorkflowToolCallStreamEvent {
  type: "tool:call";
  workflowId: string;
  call: ModelToolCall;
}

export interface WorkflowToolResultStreamEvent {
  type: "tool:result";
  workflowId: string;
  result: ToolResult;
}

export interface WorkflowFinishStreamEvent {
  type: "workflow:finish";
  workflowId: string;
  output: ChatWorkflowOutput;
}

export interface WorkflowErrorStreamEvent {
  type: "workflow:error";
  workflowId: string;
  error: SafeWorkflowError;
}
```

### 6.2 每种事件的业务语义

```txt
workflow:start
→ 本次 streamWorkflow 已被接收并获得 workflowId。
→ 不是“模型已成功开始生成”。

step:start
→ 一个可观测工作流步骤开始。
→ 仅用于 Debug / Trace，不代表该步骤一定会成功。

step:end
→ 一个步骤以 success、skipped 或 degraded 的结果结束；必须通过 status 字段显式表达。
→ 失败并终止整轮工作流时，使用 workflow:error，不额外强制发 step:end。
→ summary 只允许放安全、轻量、可调试的信息；不得放模型 raw 响应；不得用 summary 替代 status。

text:delta
→ 最终面向用户的伴侣自然语言回复的一段增量文本。
→ 只能在“最终回复流”阶段出现。
→ 不得用来传递规划文本、思维过程、工具参数、结构化 JSON、内部提示词或安全审计内容。

tool:call / tool:result
→ 对工具规划与工具执行的可观测通知。
→ V1.1 仅允许出现在最终文本流开始之前。
→ 其完整行为在阶段 3 / 5 实现；本阶段只冻结事件形状。

workflow:finish
→ 本轮成功或降级完成的唯一终止事件。
→ 必须携带完整 ChatWorkflowOutput。
→ 仅可在 Output Safety、Summary、Memory 写回等后置步骤完成后发出。

workflow:error
→ 本轮失败的唯一终止事件。
→ 必须使用 SafeWorkflowError，不得泄漏 API Key、原始请求头、完整 Provider 原始错误或不可序列化对象。
```

### 6.3 text:delta 文本聚合不变量

一次正常完成的流满足：

```ts
const renderedText = allEvents
  .filter((event) => event.type === "text:delta")
  .map((event) => event.text)
  .join("");

renderedText === finishEvent.output.text;
```

约束：

```txt
- 不得向宿主发送仅空白（trim 后为空）的 text:delta；
- 模型或 Adapter 可能产出空字符串 chunk；Workflow 应合并或丢弃这类 chunk，且不得因此破坏最终聚合文本不变量；
- text:delta 的相对顺序不得改变；
- 正常完成时，workflow:finish.output.text 必须等于所有 text:delta 拼接结果；
- 没有最终文本的成功工作流仍可发 workflow:finish，但 output.text 必须符合现有 Workflow 的有效输出规则；
- 不得在 workflow:finish 后继续发 text:delta；
- 不得在 workflow:error 后继续发任何事件。
```

### 6.4 事件顺序与终止规则

正常流程最小顺序：

```txt
workflow:start
↓
step:start / step:end（零到多个）
↓
text:delta（零到多个）
↓
step:start / step:end（Safety / Summary / Memory 等后置步骤）
↓
workflow:finish
↓
AsyncIterable 结束
```

工具流程在 V1.1 中的允许顺序：

```txt
workflow:start
↓
前置步骤
↓
tool:call / tool:result（零到多个）
↓
text:delta（最终回复）
↓
后置步骤
↓
workflow:finish
```

失败流程：

```txt
workflow:start
↓
已成功的前置事件（可选）
↓
text:delta（可选，代表已有部分文本）
↓
workflow:error
↓
AsyncIterable 结束
```

全局不变量：

```txt
- 每个 streamWorkflow 调用只生成一个 workflowId；
- 同一流中的所有事件 workflowId 必须相同；
- 每条流最多一个终止事件；
- 终止事件只能是 workflow:finish 或 workflow:error 之一；
- workflow:finish 与 workflow:error 不可同时出现；
- 正常完成必须以 workflow:finish 收口；
- streamWorkflow() 内部捕获 Workflow 执行异常后，必须 yield workflow:error 并正常结束 AsyncIterable，不得向宿主抛出未包装异常；
- 仅输入校验等同步前置错误（如 message 为空）可在 stream 开始前同步 throw；一旦已 yield workflow:start，后续错误一律通过 workflow:error 终止；
- workflow:error 之后不执行 Summary / Memory 写回；
- 已发送 text:delta 后发生 Output Safety 或后置写回错误时，不得伪装为 workflow:finish。
```

### 6.5 部分文本与后置失败语义

V1.1 的 Output Safety 是“完整回复生成后审计”，不是逐 token 实时拦截。

因此可能出现：

```txt
text:delta 已发送给 UI
↓
模型流结束
↓
Output Safety 拒绝，或 Summary / Memory 写回发生致命错误
↓
workflow:error
```

此时：

```txt
- UI 可保留已渲染的 partial text；
- UI 必须明确显示本轮未成功完成；
- 不得把该轮消息标记为“已完成 / 已成功持久化”；
- workflow:error.error.code 必须可区分 output_safety_rejected、post_process_failed 等安全错误类别；
- V1.1 不要求撤回已显示文本，也不要求恢复或重新生成。
```

## 七、SafeWorkflowError 契约

### 7.1 目标

流式错误必须可由宿主展示、记录与序列化，同时不泄漏敏感 Provider 信息。

建议定义：

```ts
export interface SafeWorkflowError {
  code:
    | "workflow_stream_not_supported"
    | "input_safety_rejected"
    | "output_safety_rejected"
    | "model_stream_failed"
    | "tool_planning_failed"
    | "tool_execution_failed"
    | "post_process_failed"
    | "workflow_failed";
  message: string;
  retryable?: boolean;
  step?: WorkflowStepName;
  details?: Record<string, string | number | boolean | null>;
}
```

约束：

```txt
- message 面向宿主与调试台，可解释但不泄密；
- details 只允许 JSON 基础值；
- 不得包含 stack、cause、request headers、API key、完整模型 raw response；
- Provider 原始异常只能在本地 Observer / 安全日志中保留，不能通过 Workflow Event 直接暴露；
- 本阶段只定义错误 DTO，不要求重构所有既有错误类。
```

### 7.2 失败与降级的区分

```txt
降级（degraded）
→ Workflow 仍能产出可信的 ChatWorkflowOutput。
→ 最终发送 workflow:finish。
→ trace / output.metadata 中记录降级信息。

失败（failed）
→ 无法产出可信且完整的最终 ChatWorkflowOutput。
→ 最终发送 workflow:error。
→ 不发送 workflow:finish。
```

示例：

```txt
Memory recall 失败，但聊天主链路可继续
→ degraded + workflow:finish。

模型在首个 text:delta 前失败，且无可用 fallback
→ workflow:error(code=model_stream_failed)。

输出文本已完成，但 Output Safety 拒绝
→ workflow:error(code=output_safety_rejected)。
```

## 八、Core Event 与 Wire Event 的边界

### 8.1 两套契约的所有权

```txt
ChatWorkflowStreamEvent
→ ai-core 的业务事件。
→ 可带 Date、ToolResult、ChatWorkflowOutput、内部 debug 字段与 unknown 原始结果。
→ 不能假设可 JSON.stringify。

ChatWorkflowStreamWireEvent
→ Demo / HTTP 宿主的传输 DTO。
→ 必须 100% JSON-safe。
→ 不能反向进入 ai-core 作为业务输入。
```

`packages/ai-core` 不得为了 HTTP 传输而依赖 Next.js、Web API Response、Node stream、NDJSON 库或 Demo DTO。

### 8.2 Wire Event 推荐形状

Demo 在后续阶段定义并使用以下等价结构：

```ts
export type ChatWorkflowStreamWireEvent =
  | {
      type: "workflow:start";
      workflowId: string;
      timestamp: string;
    }
  | {
      type: "step:start";
      workflowId: string;
      step: WorkflowStepName;
      timestamp: string;
    }
  | {
      type: "step:end";
      workflowId: string;
      step: WorkflowStepName;
      timestamp: string;
      status: WorkflowStepStatus;
      summary?: Record<string, JsonValue>;
    }
  | {
      type: "text:delta";
      workflowId: string;
      text: string;
      model?: string;
    }
  | {
      type: "tool:call";
      workflowId: string;
      call: SerializableModelToolCall;
    }
  | {
      type: "tool:result";
      workflowId: string;
      result: SerializableToolResult;
    }
  | {
      type: "workflow:finish";
      workflowId: string;
      output: SerializableChatWorkflowOutput;
    }
  | {
      type: "workflow:error";
      workflowId: string;
      error: SafeWorkflowError;
    };

export type JsonPrimitive = string | number | boolean | null;
export type JsonValue = JsonPrimitive | JsonValue[] | { [key: string]: JsonValue };
```

`SerializableChatWorkflowOutput` 的最低要求：

```txt
必须保留
- text
- model
- persona（按 JSON-safe 映射）
- emotion
- memories 的 Demo 展示 DTO
- toolResults 的 Demo 展示 DTO
- safety 的安全 DTO
- runtime / trace / debugContext 中 Demo 需要展示的安全字段
- summary / updatedSummary 的安全 DTO

必须剔除或转换
- raw
- modelOutput.raw
- Error 实例
- Function / Symbol / BigInt
- Date（转换为 ISO string）
- Map / Set / class instance（转换为普通对象或数组）
- 循环引用对象
- Provider SDK 私有对象
```

> `SerializableChatWorkflowOutput` 的精确字段由阶段 7 Demo Workbench 根据实际展示需求实现；但不得改变本阶段规定的安全边界和终止语义。

`SerializableModelToolCall` / `SerializableToolResult` 的最低映射规则（本阶段 02-03 须实现）：

```txt
SerializableModelToolCall
→ 保留 id / name / arguments
→ arguments 必须为 JSON-safe（object / array / string / number / boolean / null）；不可 JSON 化的值转为 string 或丢弃

SerializableToolResult
→ 保留 toolCallId / name / result / ok / error
→ metadata.startedAt / endedAt 转为 ISO string
→ metadata.rawArguments 按 JSON-safe 规则转换或剔除
→ result / error 中不得保留 Error 实例、Function 或循环引用
```

### 8.3 Core Event 到 Wire Event 的映射

后续 Demo 宿主必须通过单一映射函数转换：

```ts
function toChatWorkflowStreamWireEvent(event: ChatWorkflowStreamEvent): ChatWorkflowStreamWireEvent;
```

约束：

```txt
- 不允许在 route、React Client、Chat Panel 分别手写不同转换逻辑；
- timestamp 一律调用 toISOString()；
- 映射失败必须转换为可观测的传输错误；
- 不得因为某个 debug 字段不可序列化而静默吞掉 workflow:finish；
- 发生映射失败时，服务端应尽可能发送 workflow:error(code=workflow_failed 或等价安全码)，然后结束传输；
- Wire Event 的字段只能增量新增，不得在 V1.1 内修改既定 type 的语义。
```

## 九、NDJSON 网络传输约定（供后续阶段消费）

本阶段不实现 HTTP Route，但固定 V1.1 Demo 的传输选择：

```txt
POST + fetch + ReadableStream + NDJSON
```

服务端后续必须使用：

```txt
Content-Type: application/x-ndjson; charset=utf-8
Cache-Control: no-cache, no-transform
```

每一行必须是一个完整、独立的 `ChatWorkflowStreamWireEvent` JSON：

```txt
{"type":"workflow:start","workflowId":"wf_123","timestamp":"2026-06-22T12:00:00.000Z"}
{"type":"text:delta","workflowId":"wf_123","text":"你好"}
{"type":"workflow:finish","workflowId":"wf_123","output":{"text":"你好"}}
```

客户端后续消费流程：

```txt
fetch(POST /api/chat)
↓
response.body.getReader()
↓
TextDecoder 增量解码
↓
按 \n 切分完整 NDJSON 行
↓
JSON.parse
↓
校验为 ChatWorkflowStreamWireEvent
↓
按 event.type 更新聊天与调试状态
```

约束：

```txt
- 不使用 EventSource 作为 V1.1 聊天主通道；
- 不使用“一个 JSON 数组在最后一次性返回”伪装流式；
- 网络分片不等于 NDJSON 行边界，客户端必须处理半行与多行同批到达；
- 空行可忽略；非法 JSON 或未知 type 必须显示为传输 / 协议错误；
- 客户端收到 workflow:finish 或 workflow:error 后必须停止把后续事件写入当前轮状态；
- V1.1 不处理断线重连、续传与重放。
```

## 十、内部任务与最终文本流的边界

V1.1 不要求所有 AI 调用流式化。

内部结构化任务继续使用 `generate()` 或各 Provider 自有同步 / 异步方法：

```txt
- Persona load
- Input safety
- Summary load
- Memory recall
- Emotion analyze / transition
- Tool planning
- Tool execution
- Output safety
- Summary save
- Memory extract / save
```

其中：

```txt
Persona load / Summary load / Memory recall / Tool execution
→ 通常是 Provider 调用、存储读取或检索，不等于模型 generate。

Emotion analyze / Tool planning / Summary update / Memory extract
→ 可能使用模型 generate，但仍属于内部结构化任务。

最终面向用户的自然语言回复
→ 阶段 5 使用 model.stream()。
→ 只有该阶段产生 text:delta。
```

禁止：

```txt
- 将 Safety、Summary Load、Memory Recall 误写成“聊天模型生成步骤”；
- 为了判断是否需要工具，先生成一份面向用户的完整回答后丢弃；
- 让内部规划文本、JSON 或 tool arguments 混入 text:delta；
- 让 Demo 根据 provider 名称猜测哪个步骤在流式。
```

工具规划的具体 `ToolPlanningProvider`、`ToolPlan` 与模型能力档案由阶段 3 定义；本阶段仅为其预留 `tool:call` / `tool:result` 事件位置和顺序规则。

## 十一、实施子任务

### 11.1 02-01：定义并导出 Core Stream 类型

**目标**

在 `ai-core` 中定义 `ChatWorkflowStreamEvent`、各事件子类型与 `SafeWorkflowError`。

**怎么做**

```txt
1. 复用既有 WorkflowStepName、WorkflowStepStatus、ModelToolCall、ToolResult、ChatWorkflowOutput；
2. step:end 必须携带 status: WorkflowStepStatus，与 WorkflowStepTrace 对齐；
3. 新增类型文件或扩展 workflow.ts；
4. 从 ai-core 的公共 index.ts 导出；
5. 不引入 HTTP / NDJSON 类型。
```

**完成标准**

```txt
- 下游 package 可仅从 @ying-companion/ai-core 导入 Core Event 类型；
- Event union 可通过 type narrowing 可靠区分；
- 新类型不让 V1.0 现有 import 失效。
```

### 11.2 02-02：扩展 ChatWorkflow 与 CompanionCore 契约

**目标**

新增 `streamWorkflow()` 与可选 `ChatWorkflow.stream()`，同时保证 V1.0 的 `executeWorkflow()` 不变。

**怎么做**

```txt
1. ChatWorkflow.stream 使用 optional method；
2. CompanionCore.streamWorkflow 作为公开入口；
3. 未实现 stream 的 Workflow 由 CompanionCore 统一兜底 workflow_stream_not_supported 终止语义；
4. streamWorkflow 在 yield workflow:start 后不得向宿主 throw，须 yield workflow:error；
5. 本阶段允许仅以最小占位实现验证类型与事件边界，禁止伪造逐 token 输出。
```

**完成标准**

```txt
- 旧 Workflow 只实现 execute 仍能 typecheck；
- 旧宿主只调用 executeWorkflow 不需改动；
- 新宿主可编译调用 streamWorkflow；
- stream 不支持场景有确定、可观察的错误语义。
```

### 11.3 02-03：定义 Wire DTO 与单一映射边界

**目标**

在 Demo / 宿主层定义 JSON-safe Wire Event，并锁定 Core Event 不直接跨网络。

**怎么做**

```txt
1. 定义 JsonValue、Wire Event、SerializableChatWorkflowOutput 的最小骨架；
2. 定义 SerializableModelToolCall / SerializableToolResult 并按 8.2 映射规则转换 arguments 与 metadata Date；
3. 定义单一 toChatWorkflowStreamWireEvent() 映射函数签名；
4. 本阶段可不接 Route，但必须明确 raw 与 Date 的剔除 / 转换规则；
5. 不把 Wire DTO 导入 ai-core。
```

**完成标准**

```txt
- Core Event 与 Wire Event 的类型不可误用；
- 所有 Wire Event 均可 JSON.stringify；
- 流式 finish / error 在网络层有明确表示。
```

### 11.4 02-04：补齐契约说明与最小验证脚本

**目标**

让后续阶段能通过最小本地验证确认类型、事件顺序和序列化边界正确。

**怎么做**

```txt
1. 在 model-runtime-demo 或合适的开发入口新增仅开发用途的契约验证脚本；
2. 构造最小 start → text:delta → finish 事件并映射为 Wire Event；
3. 构造 workflow_stream_not_supported 与 post_process_failed 错误事件；
4. 对每个 Wire Event 执行 JSON.stringify / JSON.parse；
5. 在 console 输出事件序列、聚合文本和序列化结果。
```

**完成标准**

```txt
- Console 可展示正常完成、流不支持、后置失败三种序列；
- 正常完成时 delta 聚合文本等于 finish.output.text；
- Wire Event 不含 raw / Date / Error 实例；
- 不要求单元测试或 e2e 测试。
```

## 十二、人工验收场景

### 场景 A：V1.0 兼容调用

```txt
给一个只调用 executeWorkflow() 的旧宿主。
↓
不修改宿主调用代码。
↓
聊天结果、ChatWorkflowOutput、现有 Debug Context 仍正常返回。
```

验收：旧调用无 TypeScript 报错、无运行时回归。

### 场景 B：旧自定义 Workflow

```txt
提供一个只实现 execute() 的自定义 ChatWorkflow。
↓
createCompanionCore({ workflow })。
↓
executeWorkflow() 成功。
↓
streamWorkflow()。
```

验收：

```txt
- 自定义 Workflow 不因缺少 stream() 而 typecheck 失败；
- streamWorkflow 先发 workflow:start；
- 再发 workflow:error(code=workflow_stream_not_supported)；
- 不发 text:delta 或 workflow:finish；
- 事件流结束。
```

### 场景 C：正常流事件顺序

```txt
构造 start → step:start → step:end(status=success) → text:delta("你") → text:delta("好") → finish 的事件流。
```

验收：

```txt
- workflowId 始终一致；
- step:end 携带显式 status，不依赖 summary 隐式表达；
- 聚合结果为“你好”；
- finish.output.text 为“你好”；
- finish 后无更多事件；
- 每个 Wire Event 均可 JSON.stringify。
```

### 场景 D：文本已输出后的 Safety 拒绝

```txt
构造 text:delta("部分回复") 后发生 output_safety_rejected。
```

验收：

```txt
- 发 workflow:error；
- 不发 workflow:finish；
- UI / console 可区分“已有 partial text，但本轮失败”；
- error 不包含 provider raw 内容或 stack。
```

### 场景 E：Wire 序列化边界

```txt
构造含 raw、Date、Error、函数、Map 的 ChatWorkflowOutput / ToolResult。
↓
通过 toChatWorkflowStreamWireEvent 转换。
```

验收：

```txt
- raw 不出现在 Wire Event；
- Date 变为 ISO string；
- Error / 函数 / Map 不直接出现在 JSON；
- 如关键数据无法安全转换，转换过程产生可观测错误，而不是静默损坏 finish 事件。
```
