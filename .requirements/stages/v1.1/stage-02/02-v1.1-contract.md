# AI Companion Core V1.1 - 阶段 2：V1.1 契约、事件、Wire 协议与兼容边界实施文档

## 一、阶段目标

在改造 `SimpleChatWorkflow`、接入模型 Provider 策略、实现 Ollama Adapter 与升级 Demo 网络层之前，先冻结 V1.1 的公共契约。

本阶段交付：

1. Core 的双路工作流调用边界；
2. Core 内部流事件、完成与错误语义；
3. `CoreObserver` 与流事件的职责边界；
4. Core Event 到 HTTP Wire Event 的序列化边界；
5. NDJSON 的后续传输约定；
6. 旧宿主与旧自定义 Workflow 的兼容策略。

本阶段不实现真实流式聊天、不重构 `SimpleChatWorkflow`、不接入 Ollama、不实现模型能力档案或工具规划、不修改 Demo 聊天 Route。

> 原则：先冻结稳定的协议，再分别实现模型能力、工作流、Adapter 与宿主消费层；任何后续阶段不得靠猜测补齐本阶段应定义的语义。

- `ai-core` typecheck、lint、build 通过；
- 完成本文件的人工契约验证。

## 五、双路工作流调用契约

### 5.1 CompanionCore 公共 API

```ts
interface CompanionCore {
  executeWorkflow(input: ChatWorkflowInput): Promise<ChatWorkflowOutput>;

  streamWorkflow(
    input: ChatWorkflowInput,
  ): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

语义：

```txt
executeWorkflow()
→ 返回完整 ChatWorkflowOutput。
→ 服务旧宿主、后台任务、结构化调用与非流式调试。
→ 不因 V1.1 stream 改造改变既有成功、降级、错误行为。

streamWorkflow()
→ 返回 Core 内部事件流。
→ 服务聊天 UI、实时 Debug Workbench 与未来任意宿主。
→ 不返回 HTTP Response、ReadableStream 或 NDJSON 字符串。
```

### 5.2 不允许用 streamWorkflow 取代 executeWorkflow

禁止：

```ts
async executeWorkflow(input) {
  for await (const event of this.streamWorkflow(input)) {
    // 拼回完整输出
  }
}
```

原因：V1.0 的 `executeWorkflow()` 具备稳定行为；阶段 4 的目标是抽取共享步骤函数，而不是让一个公开入口伪装成另一个入口。

阶段 4 / 5 可以复用内部步骤函数，但必须保留两条公开路径的清晰语义。

### 5.3 ChatWorkflow 的兼容扩展

为避免既有自定义 Workflow 发生 TypeScript 破坏性变更：

```ts
interface ChatWorkflow extends CoreProvider {
  execute(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): Promise<ChatWorkflowOutput>;

  stream?(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

兼容规则：

```txt
旧自定义 Workflow
→ 仅实现 execute() 仍可 typecheck。
→ 旧宿主调用 executeWorkflow() 行为不变。

宿主调用 streamWorkflow()
→ Workflow 实现 stream()：CompanionCore 委托其输出。
→ Workflow 未实现 stream()：CompanionCore 统一发出：
   workflow:start
   → workflow:error(code=workflow_stream_not_supported)
   → 结束。
→ 不得伪造逐字输出。

SimpleChatWorkflow
→ 阶段 5 必须实现真实 stream()。
```

### 5.4 不支持取消与恢复

V1.1 不为 `streamWorkflow()` 增加 `AbortSignal`、续传 cursor、断线恢复或 token 重放。该能力会影响 Provider 取消、写回幂等、NDJSON 重连与前端状态机，留待后续版本单独设计。

## 六、CoreObserver 与 Stream Event 的关系

V1.0 已有 `CoreObserver`，其中包含 `workflow:start`、`workflow:step`、`workflow:end`、`workflow:error` 等旁路事件。V1.1 新增 `ChatWorkflowStreamEvent`，两者不能混用。

```txt
CoreObserver
→ 旁路可观测通道。
→ 用于日志、调试、持久化与诊断。
→ workflow:end 是 Observer 视角的工作流结束。

ChatWorkflowStreamEvent
→ streamWorkflow() 的主协议。
→ 聊天 UI 与 NDJSON 消费层依赖它。
→ workflow:finish 是流协议的成功/降级终止。
→ workflow:error 是流协议的失败终止。
```

约束：

```txt
- SimpleChatWorkflow 实现 stream() 后仍必须 emit CoreObserver 事件，保持 V1.0 调试能力；
- Demo Timeline 以 ChatWorkflowStreamEvent 为主时间线；
- Observer 的 workflow:step 与 Stream 的 step:start / step:end 不得共用同一 UI handler；
- workflow:end（Observer）不等于 workflow:finish（Stream）。
```

## 七、Core 流事件契约

### 7.1 事件类型

```ts
export type ChatWorkflowStreamEvent =
  | WorkflowStartStreamEvent
  | WorkflowStepStartStreamEvent
  | WorkflowStepEndStreamEvent
  | WorkflowTextDeltaStreamEvent
  | WorkflowToolCallStreamEvent
  | WorkflowToolResultStreamEvent
  | WorkflowFinishStreamEvent
  | WorkflowErrorStreamEvent;

export interface WorkflowStartStreamEvent {
  type: "workflow:start";
  workflowId: string;
  timestamp: Date;
}

export interface WorkflowStepStartStreamEvent {
  type: "step:start";
  workflowId: string;
  step: WorkflowStepName;
  timestamp: Date;
}

export interface WorkflowStepEndStreamEvent {
  type: "step:end";
  workflowId: string;
  step: WorkflowStepName;
  timestamp: Date;
  status: WorkflowStepStatus;
  summary?: Record<string, unknown>;
}

export interface WorkflowTextDeltaStreamEvent {
  type: "text:delta";
  workflowId: string;
  text: string;
  model?: string;
}

export interface WorkflowToolCallStreamEvent {
  type: "tool:call";
  workflowId: string;
  call: ModelToolCall;
}

export interface WorkflowToolResultStreamEvent {
  type: "tool:result";
  workflowId: string;
  result: ToolResult;
}

export interface WorkflowFinishStreamEvent {
  type: "workflow:finish";
  workflowId: string;
  output: ChatWorkflowOutput;
}

export interface WorkflowErrorStreamEvent {
  type: "workflow:error";
  workflowId: string;
  error: SafeWorkflowError;
}
```

### 7.2 事件语义

```txt
workflow:start
→ streamWorkflow 已接收输入并分配 workflowId。
→ 不代表模型已经开始生成。

step:start
→ 可观测步骤开始。

step:end
→ 对应 step:start 的唯一结束事件。
→ status 必须为 success / skipped / degraded / failed 之一。
→ summary 只能包含安全、轻量、可调试数据；不得承载 raw，也不得替代 status。

text:delta
→ 最终面向用户的伴侣自然语言回复片段。
→ 仅在最终自然语言回复阶段出现。
→ 不得传递规划文本、思维过程、工具参数、结构化 JSON、内部提示词或安全审计内容。

tool:call / tool:result
→ 工具规划与执行的可观测通知。
→ V1.1 只允许出现在最终文本流开始前。
→ 阶段 3 / 5 冻结具体工具规划行为；本阶段只冻结事件形状与顺序。

workflow:finish
→ 成功或降级完成的唯一终止事件。
→ 必须携带完整 ChatWorkflowOutput。
→ 只能在 Output Safety、Summary、Memory 等后置处理完成后发出。

workflow:error
→ 失败的唯一终止事件。
→ 必须携带 SafeWorkflowError。
→ 不得泄漏 API Key、原始请求头、Provider raw、堆栈或不可序列化对象。
```

### 7.3 步骤闭环不变量

```txt
- 每个已发送 step:start 的步骤，必须恰好发送一个同 step 的 step:end；
- 若步骤失败：先发送 step:end(status="failed")，再发送 workflow:error；
- 若在任何 step:start 前发生错误：允许直接 workflow:error；
- skipped 与 degraded 也是完成状态，必须通过 step:end 的 status 表达；
- workflow:error 后不再发送任何事件；
- workflow:finish 后不再发送任何事件。
```

此规则确保 Stream Timeline、`WorkflowTrace` 与 Debug UI 不会出现“开始但永不结束”的悬挂步骤。

### 7.4 text:delta 文本聚合不变量

正常完成时：

```ts
const renderedText = allEvents
  .filter((event) => event.type === "text:delta")
  .map((event) => event.text)
  .join("");

renderedText === finishEvent.output.text;
```

约束：

```txt
- 不得发送 text === "" 的空字符串 delta；
- 仅包含空白字符的 delta 不得被直接丢弃；它可能是英文单词、Markdown、代码或自然语言之间不可丢失的分隔符；
- Workflow 可以合并连续 chunk，包括空白 chunk，但合并后 delta 的拼接结果必须仍严格等于最终 output.text；
- text:delta 顺序不得改变；
- workflow:finish 后不得继续发送 text:delta；
- workflow:error 后不得继续发送任何事件；
- 不得对 delta 使用 trim() 后再决定是否删除；
- 若模型最终没有文本，是否允许成功由现有 Workflow 的有效输出规则决定；一旦成功，finish.output.text 仍必须与 delta 聚合结果一致。
```

示例：

```txt
模型 chunk："hello"、" "、"world"
合法输出：
- text:delta("hello")
- text:delta(" ")
- text:delta("world")
或合并为：
- text:delta("hello ")
- text:delta("world")

禁止输出：
- text:delta("hello")
- 丢弃 " "
- text:delta("world")
```

### 7.5 事件顺序与终止规则

正常流程：

```txt
workflow:start
↓
step:start / step:end（零到多个前置步骤）
↓
text:delta（零到多个最终文本片段）
↓
step:start / step:end（零到多个后置步骤）
↓
workflow:finish
↓
AsyncIterable 结束
```

工具流程：

```txt
workflow:start
↓
前置步骤
↓
tool:call / tool:result（零到多个）
↓
text:delta（最终回复）
↓
后置步骤
↓
workflow:finish
```

失败流程：

```txt
workflow:start
↓
已完成的前置事件（可选）
↓
已开始步骤的 step:end(status=failed)（可选）
↓
text:delta（可选，已有部分文本）
↓
workflow:error
↓
AsyncIterable 结束
```

全局规则：

```txt
- 每个 streamWorkflow 调用只生成一个 workflowId；
- 同一流中的所有事件 workflowId 必须相同；
- 每条流最多一个终止事件；
- 终止事件只能是 workflow:finish 或 workflow:error 之一；
- 正常完成必须以 workflow:finish 收口；
- streamWorkflow 捕获运行时异常后，默认 yield workflow:error 并正常结束 AsyncIterable；
- 仅输入校验等同步前置错误（例如 message 为空）允许在 stream 开始前同步 throw；
- 一旦已 yield workflow:start，后续错误一律通过 workflow:error 终止；
- Output Safety 拒绝为失败，不能伪装为 finish；
- Summary / Memory 的可恢复失败不得自动升级为 workflow:error，必须按本文件第九章处理。
```

## 八、SafeWorkflowError 契约

```ts
export interface SafeWorkflowError {
  code:
    | "workflow_stream_not_supported"
    | "input_safety_rejected"
    | "output_safety_rejected"
    | "model_stream_failed"
    | "tool_planning_failed"
    | "tool_execution_failed"
    | "post_process_failed"
    | "workflow_failed";
  message: string;
  retryable?: boolean;
  step?: WorkflowStepName;
  details?: Record<string, string | number | boolean | null>;
}
```

约束：

```txt
- message 面向宿主与调试台，可解释但不泄密；
- details 只允许 JSON 基础值；
- 不得包含 stack、cause、headers、API key、完整 raw response；
- Provider 原始异常可在本地 Observer / 安全日志保留，但不得进入 Stream Event；
- 本阶段只定义安全错误 DTO，不要求重构所有既有错误类。
```

## 九、失败、降级与后置处理语义

### 9.1 降级与失败

```txt
降级（degraded）
→ Workflow 仍能产出可信、可交付的 ChatWorkflowOutput。
→ 最终发 workflow:finish。
→ trace / metadata 记录降级原因。

失败（failed）
→ 无法产出可信且完整的最终 ChatWorkflowOutput。
→ 最终发 workflow:error。
→ 不发 workflow:finish。
```

### 9.2 V1.1 后置步骤默认策略

V1.0 已确立“Memory / Emotion 失败不应打断聊天主链路”的原则。V1.1 必须延续这一原则。

```txt
Output Safety 拒绝
→ failed。
→ workflow:error(code=output_safety_rejected)。

最终模型流在首个 delta 前失败，且无可用 fallback
→ failed。
→ workflow:error(code=model_stream_failed)。

Summary load / save 失败，但最终文本已通过 Output Safety
→ 默认 degraded。
→ 对应 step:end(status=degraded)。
→ workflow:finish。

Memory recall / extract / save 失败，但最终文本已通过 Output Safety
→ 默认 degraded。
→ 对应 step:end(status=degraded)。
→ workflow:finish。

Emotion 分析失败，但可回退到已有或 neutral 情绪
→ degraded。
→ workflow:finish。

未来出现被明确标注为 mandatory 的后置 Provider
→ 才允许因其失败使用 post_process_failed 终止；
→ V1.1 的 Summary、Memory、Emotion 不属于 mandatory。
```

### 9.3 已输出文本后的失败

Output Safety 是完整回复生成后的审计，不是逐 token 拦截，因此可能发生：

```txt
text:delta 已发送
↓
模型流结束
↓
Output Safety 拒绝
↓
workflow:error
```

此时：

```txt
- UI 可保留 partial text；
- UI 必须显示“本轮未成功完成”；
- 不得标记消息为已成功持久化；
- 不要求撤回、重试或恢复生成。
```

若 Summary / Memory 等默认可降级后置步骤失败：

```txt
- UI 仍显示本轮完成；
- workflow:finish 正常发送；
- Timeline / trace 明确显示相关步骤为 degraded；
- output.metadata / Debug Context 记录降级原因；
- 宿主不得把该轮误标为“所有写回均成功”。
```

## 十、Core Event 与 Wire Event 的边界

### 10.1 所有权

```txt
ChatWorkflowStreamEvent
→ ai-core 的业务事件。
→ 可包含 Date、ToolResult、ChatWorkflowOutput、内部 Debug 字段与 unknown 原始结果。
→ 不保证可 JSON.stringify。

ChatWorkflowStreamWireEvent
→ Demo / HTTP 宿主的传输 DTO。
→ 必须完全 JSON-safe。
→ 不得反向作为 ai-core 的业务输入。
```

`packages/ai-core` 不得因此依赖 Next.js、Web API Response、Node Stream、NDJSON 库或 Demo DTO。

### 10.2 Wire Event 推荐形状

```ts
export type JsonPrimitive = string | number | boolean | null;
export type JsonValue = JsonPrimitive | JsonValue[] | { [key: string]: JsonValue };

export type ChatWorkflowStreamWireEvent =
  | { type: "workflow:start"; workflowId: string; timestamp: string }
  | { type: "step:start"; workflowId: string; step: WorkflowStepName; timestamp: string }
  | {
      type: "step:end";
      workflowId: string;
      step: WorkflowStepName;
      timestamp: string;
      status: WorkflowStepStatus;
      summary?: Record<string, JsonValue>;
    }
  | { type: "text:delta"; workflowId: string; text: string; model?: string }
  | { type: "tool:call"; workflowId: string; call: SerializableModelToolCall }
  | { type: "tool:result"; workflowId: string; result: SerializableToolResult }
  | {
      type: "workflow:finish";
      workflowId: string;
      output: SerializableChatWorkflowOutput;
    }
  | { type: "workflow:error"; workflowId: string; error: SafeWorkflowError };
```

`SerializableChatWorkflowOutput` 最低要求：

```txt
保留：
- text、model、persona、emotion；
- Demo 需要展示的 memories、toolResults、safety、summary、trace、runtime、debugContext；

剔除或转换：
- raw、modelOutput.raw；
- Error、Function、Symbol、BigInt；
- Date（转换 ISO string）；
- Map / Set / class instance（转换普通对象或数组）；
- 循环引用；
- Provider SDK 私有对象。
```

`SerializableModelToolCall` 保留 `id / name / arguments`；`arguments` 必须 JSON-safe。

`SerializableToolResult` 保留 `toolCallId / name / result / ok / error`；时间字段转 ISO string；不得传递 Error 实例、函数或循环引用。

### 10.3 单一映射函数

```ts
function toChatWorkflowStreamWireEvent(
  event: ChatWorkflowStreamEvent,
): ChatWorkflowStreamWireEvent;
```

约束：

```txt
- Route、React Client、Chat Panel 不得分别手写映射；
- timestamp 一律转换为 ISO string；
- 关键数据无法安全映射时必须可观测，不能静默损坏 finish；
- 映射失败时服务端应尽可能发送 workflow:error(code=workflow_failed 或等价安全码)，随后结束；
- Wire Event 字段只能增量新增，不得在 V1.1 内改变既定语义。
```

## 十一、NDJSON 网络传输约定

本阶段不实现 HTTP Route，但固定 V1.1 Demo 后续使用：

```txt
POST + fetch + ReadableStream + NDJSON
```

服务端：

```txt
Content-Type: application/x-ndjson; charset=utf-8
Cache-Control: no-cache, no-transform
```

每一行是独立完整的 `ChatWorkflowStreamWireEvent` JSON：

```txt
{"type":"workflow:start","workflowId":"wf_123","timestamp":"2026-06-22T12:00:00.000Z"}
{"type":"text:delta","workflowId":"wf_123","text":"你好"}
{"type":"workflow:finish","workflowId":"wf_123","output":{"text":"你好"}}
```

客户端：

```txt
fetch(POST /api/chat)
↓
response.body.getReader()
↓
TextDecoder 增量解码
↓
按 \n 切分完整 NDJSON 行
↓
JSON.parse + Wire Event 校验
↓
按 event.type 更新聊天与调试状态
```

约束：

```txt
- 不使用 EventSource 作为 V1.1 聊天主通道；
- 不使用最后一次性返回 JSON 数组伪装流式；
- 网络分片不等于 NDJSON 行边界，客户端必须处理半行与多行同批到达；
- 空行可忽略；非法 JSON 或未知 type 必须显示为协议错误；
- 客户端收到 finish 或 error 后停止写入当前轮状态；
- V1.1 不处理断线重连、续传与重放。
```

## 十二、内部任务与最终文本流的边界

V1.1 不要求全部 AI 调用流式化。

```txt
通常为 Provider / 存储调用，不等于模型 generate：
- Persona load
- Input safety
- Summary load
- Memory recall
- Tool execution

可能使用模型 generate 的内部结构化任务：
- Emotion analyze / transition
- Tool planning
- Summary update
- Memory extract

唯一产生 text:delta 的阶段：
- 最终面向用户的自然语言回复，阶段 5 使用 model.stream()。
```

禁止：

```txt
- 把 Safety、Summary Load、Memory Recall 误写为聊天模型生成；
- 为判断工具调用先生成一份面向用户的完整回答后丢弃；
- 让规划 JSON、工具参数、内部 Prompt 或思维过程进入 text:delta；
- 让 Demo 根据 provider 名称猜测流程行为。
```

阶段 3 定义 `ToolPlanningProvider`、`ToolPlan`、模型能力档案；本阶段只预留 `tool:call` 与 `tool:result` 的协议位置。

## 十三、实施子任务

### 13.1 02-01：定义并导出 Core Stream 类型

**目标**

在 `ai-core` 定义 `ChatWorkflowStreamEvent`、各事件子类型与 `SafeWorkflowError`。

**怎么做**

```txt
1. 复用既有 WorkflowStepName、WorkflowStepStatus、ModelToolCall、ToolResult、ChatWorkflowOutput；
2. 定义 step:start / step:end 闭环约束；
3. 定义 text delta 的严格聚合约束；
4. 新增类型文件或扩展 workflow.ts；
5. 从 ai-core 公共 index.ts 导出；
6. 不引入 HTTP / NDJSON 类型。
```

**完成标准**

```txt
- 下游 package 可仅从 @ying-companion/ai-core 导入 Core Event 类型；
- Event union 可可靠 type narrowing；
- 新类型不破坏 V1.0 import。
```

### 13.2 02-02：扩展 ChatWorkflow 与 CompanionCore 契约

**目标**

新增 `streamWorkflow()` 与可选 `ChatWorkflow.stream()`，保持 V1.0 `executeWorkflow()` 不变。

**怎么做**

```txt
1. ChatWorkflow.stream 使用 optional method；
2. CompanionCore.streamWorkflow 作为公开入口；
3. 未实现 stream 的 Workflow 由 CompanionCore 统一发送 workflow_stream_not_supported；
4. yield workflow:start 后不得向宿主抛出未包装异常，必须发送 workflow:error；
5. 本阶段允许最小占位验证类型边界，禁止伪造 token stream。
```

**完成标准**

```txt
- 旧 Workflow 仅实现 execute 仍可 typecheck；
- 旧宿主只调用 executeWorkflow 不需修改；
- 新宿主可编译调用 streamWorkflow；
- stream 不支持场景具备确定、可观察的终止语义。
```

### 13.3 02-03：定义 Wire DTO 与单一映射边界

**目标**

在 Demo / 宿主层定义 JSON-safe Wire Event，确保 Core Event 不直接跨网络。

**怎么做**

```txt
1. 定义 JsonValue、Wire Event、SerializableChatWorkflowOutput 最小骨架；
2. 定义 SerializableModelToolCall / SerializableToolResult；
3. 定义单一 toChatWorkflowStreamWireEvent() 映射函数签名；
4. 明确 raw 与 Date 的剔除 / 转换规则；
5. Wire DTO 不得导入 ai-core。
```

**完成标准**

```txt
- Core Event 与 Wire Event 不可误用；
- 每个 Wire Event 可 JSON.stringify / JSON.parse；
- finish / error 在网络层有明确表达。
```

### 13.4 02-04：最小契约验证脚本

**目标**

让后续阶段能用本地 Console 验证类型、事件顺序、失败闭环、文本聚合与序列化边界。

**怎么做**

```txt
1. 在 model-runtime-demo 或合适开发入口新增契约验证脚本；
2. 构造正常 start → step:start → step:end(success) → text delta → finish；
3. 构造已开始步骤失败：step:start → step:end(failed) → workflow:error；
4. 构造 output_safety_rejected 与 memory:save degraded 两种后置场景；
5. 构造含空白 delta 的英文输出，例如 hello / 空格 / world；
6. 每个 Wire Event 执行 JSON.stringify / JSON.parse；
7. Console 输出事件序列、聚合文本、状态和序列化结果。
```

**完成标准**

```txt
- Console 展示正常完成、流不支持、步骤失败、Safety 失败、可恢复写回降级；
- 正常完成时 delta 聚合严格等于 finish.output.text；
- 空白分隔符不会丢失；
- Wire Event 不含 raw / Date / Error 实例；
- 不要求单元测试或 e2e 测试。
```

## 十四、人工验收场景

### 场景 A：V1.0 兼容调用

```txt
旧宿主仅调用 executeWorkflow()。
↓
不修改宿主代码。
↓
聊天结果、ChatWorkflowOutput、Debug Context 保持正常。
```

### 场景 B：旧自定义 Workflow

```txt
自定义 ChatWorkflow 仅实现 execute()。
↓
executeWorkflow() 成功。
↓
streamWorkflow()。
```

验收：

```txt
- 自定义 Workflow typecheck 正常；
- 事件为 workflow:start → workflow:error(workflow_stream_not_supported)；
- 不发 text:delta 或 workflow:finish；
- 事件流结束。
```

### 场景 C：正常事件与空白文本

```txt
事件：start → step:start → step:end(success)
→ text:delta("hello") → text:delta(" ") → text:delta("world") → finish。
```

验收：

```txt
- workflowId 一致；
- step:end 有显式 success；
- 聚合文本与 finish.output.text 都是 "hello world"；
- finish 后无更多事件；
- 所有 Wire Event 可 JSON.stringify。
```

### 场景 D：步骤失败闭环

```txt
step:start(memory:save)
↓
Provider 失败
↓
step:end(memory:save, failed)
↓
workflow:error
```

验收：每个 start 有 end，Timeline 无悬挂步骤。

### 场景 E：Output Safety 拒绝

```txt
text:delta("部分回复")
↓
output safety 拒绝
↓
workflow:error(output_safety_rejected)
```

验收：UI 可区分“已有 partial text，但本轮失败”；不发 finish；错误不泄漏 raw 或 stack。

### 场景 F：Memory 写回可恢复失败

```txt
text:delta 完成
↓
memory:save 失败
↓
step:end(status=degraded)
↓
workflow:finish
```

验收：回复完成；Trace 标记降级；UI 可查看写回未完成原因；不把这轮标记为全部写回成功。

### 场景 G：Wire 序列化边界

```txt
构造含 raw、Date、Error、函数、Map 的 ChatWorkflowOutput / ToolResult。
↓
通过 toChatWorkflowStreamWireEvent 转换。
```

验收：raw 不进入 Wire；Date 变 ISO；Error / 函数 / Map 不直接进入 JSON；关键映射失败可观测。
