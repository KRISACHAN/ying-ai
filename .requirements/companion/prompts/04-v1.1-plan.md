# AI Companion Core V1.1 实施方案

> 版本目标：在 V1.0 Core SDK 的基础上，完成「Persona 扩展与称呼、工作流级流式聊天、多模型 Provider 策略与 Ollama 接入、调试工作台升级、文档同步」。
>
> V1.1 只聚焦本地开发与 Core / SDK 能力；不引入用户系统、鉴权、部署、商业化与产品正式 UI。

---

## 前置基线

V1.1 以 `prod` 分支中已完成的 V1.0（tag `v1.0`）为唯一实现基线。

V1.0 已具备：

```txt
Model Runtime
├── OpenAI-compatible 模型实现
├── generate / stream
├── 主模型重试
├── fallback 模型
└── runtime 信息

AI Core SDK
├── Provider 抽象与注入
├── Persona
├── Safety
├── Memory / RAG
├── Emotion
├── Tool Registry
├── Summary
├── SimpleChatWorkflow
└── CoreObserver / Workflow Trace

Debug Workbench
├── 本地模型配置
├── 会话与消息持久化
├── 记忆、情绪、摘要查看
└── Workflow / Runtime 可观测信息
```

V1.1 不重做 V1.0 Provider 边界，也不将第三方 SDK、数据库、环境变量直接写入 `packages/ai-core`。

## V1.1 核心目标

将当前“完整执行后一次性返回回复”的 Core，升级为：

```txt
可选择模型 Provider
↓
可配置伴侣 Persona（含用户称呼、外貌与兴趣设定）
↓
可执行完整聊天工作流
↓
可向宿主连续输出结构化流事件
↓
用户看到伴侣回复逐字生成
↓
流结束后完成 Safety、Summary、Memory 写回与最终结果收口
```

V1.1 完成后，宿主应可以：

1. 在 Demo 中配置伴侣对用户的称呼、用户显示名，以及身高、体重、发型、身材、爱好等设定；
2. 在 Demo 中选择 OpenAI-compatible 或 Ollama 模型；
3. 在 Demo 中看到真实流式聊天回复；
4. 在 Demo 中查看本次工作流事件、模型 runtime、最终 Persona、Prompt、记忆、情绪、工具执行与写回结果；
5. 在不修改 `ai-core` 业务逻辑的前提下继续新增模型 Adapter。

## 阶段 1：Persona 扩展与 Prompt 构建升级

### 目标

使 Persona 能表达伴侣对用户的称呼，以及伴侣自身的外貌、兴趣等设定。

### 完成标准

- `CompanionPersona` 新增 `userDisplayName`、`userAddress`；
- 新增 `profile.hobbies` 与 `appearance`；
- 旧 Persona 配置保持兼容；
- Prompt Builder 仅渲染有效字段；
- `systemPrompt` 是结构化 Persona 的补充，而不是替代；
- Demo 可编辑并实时使用这些配置；
- 调试面板可查看最终 Persona 与完整 system prompt。

### 01-persona-profile.md

#### Persona 扩展

```ts
interface CompanionPersona {
  id: string;
  name: string;
  gender: CompanionGender;

  relationship?: string;
  personality?: string;
  speakingStyle?: string;
  background?: string;
  systemPrompt?: string;

  userDisplayName?: string;
  userAddress?: string;

  profile?: {
    hobbies?: string[];
  };

  appearance?: {
    heightCm?: number;
    weightKg?: number;
    hair?: string;
    bodyType?: string;
    additionalTraits?: Record<string, string>;
  };

  metadata?: Record<string, unknown>;
}
```

#### 字段约定

```txt
userDisplayName
→ 用户名字，例如：陈大鱼头

userAddress
→ 伴侣对用户的日常称呼，例如：鱼头、亲爱的、宝贝
→ 是建议称呼，不强制每句话都使用

profile.hobbies
→ 伴侣自己的兴趣，例如：烘焙、电影、旅行

appearance.heightCm / weightKg
→ 数值字段；拼入 Prompt 时显式补充 cm / kg

appearance.hair / bodyType
→ 自然语言描述，例如：黑色长直发、匀称

appearance.additionalTraits
→ 瞳色、穿衣风格、声音、常用饰品等后续扩展
```

#### Prompt 构建原则

1. “伴侣自身设定”与“用户信息”必须分区；
2. 缺失字段不得输出“未知”“未设置”等噪音；
3. `systemPrompt` 应拼接在结构化 Persona 后作为补充指令；
4. 不把长篇静态 Persona 重复拼入 Summary 或 Memory；
5. Persona 配置变更仅影响后续工作流，不回写为 Memory。

#### 可观测结果

配置：

```txt
用户名字：陈大鱼头
用户称呼：鱼头
伴侣爱好：烘焙、电影
身高：165 cm
发型：黑色长直发
身材：匀称
```

验收：

```txt
- Prompt Preview 中伴侣设定与用户信息分区清晰
- 伴侣可自然使用“鱼头”称呼用户
- 伴侣可在合适话题中提及自己的兴趣或设定
- 未配置字段不出现在 system prompt 中
```

## 阶段 2：V1.1 契约、事件、Wire 协议与兼容边界

### 目标

在改动工作流前，锁定 Core 公共 API、流事件、错误语义、网络传输语义与兼容策略。

### 完成标准

- `executeWorkflow()` 保留；
- 新增 `streamWorkflow()`；
- 定义 Core Event 与 Wire Event；
- 明确事件顺序、完成语义、错误语义；
- 明确内部结构化任务继续使用 `generate()`；
- 明确旧宿主不会因 V1.1 失效；
- 新增 V1.1 stage 文档目录。

### 02-v1.1-contract.md

#### 双路调用路径

```ts
core.executeWorkflow(input);
core.streamWorkflow(input);
```

```txt
executeWorkflow
→ 返回完整 ChatWorkflowOutput
→ 用于旧宿主兼容、后台任务、结构化处理、非流式调试

streamWorkflow
→ 返回 AsyncIterable<ChatWorkflowStreamEvent>
→ 用于聊天 UI 和实时调试面板
→ 正常完成时最后必须发送 workflow:finish
```

#### Core 流事件定义

```ts
type ChatWorkflowStreamEvent =
  | { type: "workflow:start"; workflowId: string; timestamp: Date }
  | { type: "step:start"; workflowId: string; step: WorkflowStepName; timestamp: Date }
  | {
      type: "step:end";
      workflowId: string;
      step: WorkflowStepName;
      timestamp: Date;
      summary?: Record<string, unknown>;
    }
  | { type: "text:delta"; workflowId: string; text: string; model?: string }
  | { type: "tool:call"; workflowId: string; call: ModelToolCall }
  | { type: "tool:result"; workflowId: string; result: ToolResult }
  | { type: "workflow:finish"; workflowId: string; output: ChatWorkflowOutput }
  | { type: "workflow:error"; workflowId: string; error: SafeWorkflowError };
```

#### Core Event 与 Wire Event 必须分离

Core Event 允许包含 `Date`、内部调试字段和 `unknown` 原始结果；网络层不得直接透传它。

```ts
type ChatWorkflowStreamWireEvent =
  | { type: "workflow:start"; workflowId: string; timestamp: string }
  | { type: "step:start"; workflowId: string; step: WorkflowStepName; timestamp: string }
  | {
      type: "step:end";
      workflowId: string;
      step: WorkflowStepName;
      timestamp: string;
      summary?: Record<string, unknown>;
    }
  | { type: "text:delta"; workflowId: string; text: string; model?: string }
  | { type: "tool:call"; workflowId: string; call: ModelToolCall }
  | { type: "tool:result"; workflowId: string; result: SerializableToolResult }
  | { type: "workflow:finish"; workflowId: string; output: SerializableChatWorkflowOutput }
  | { type: "workflow:error"; workflowId: string; error: SafeWorkflowError };
```

约束：

```txt
- timestamp 在 Wire Event 中一律为 ISO string
- raw、Error 实例、函数、循环引用对象不得进入 Wire Event
- 需要展示的 runtime、trace、prompt、memory、emotion 必须先映射为 JSON-safe DTO
- 网络层序列化失败必须视为工作流传输错误并可观测
```

#### 网络传输协议

V1.1 Demo 固定使用：

```txt
POST + fetch + ReadableStream + NDJSON
```

服务端：

```txt
Content-Type: application/x-ndjson; charset=utf-8
每一行是一个完整 JSON 的 ChatWorkflowStreamWireEvent
```

前端：

```txt
fetch POST 聊天请求
↓
读取 response.body
↓
按换行切分 NDJSON
↓
JSON.parse
↓
按 event.type 分发 UI 状态
```

不使用 `EventSource` 作为 V1.1 聊天主通道，因为 `EventSource` 的 GET 语义不适合携带复杂聊天 POST 输入。

## 阶段 3：模型 Provider 策略、模型能力档案与工具规划协议

### 目标

使 Workflow 只依赖模型的实际能力，而不是 Adapter 名称；同时避免“为判断是否调用工具先生成一遍最终回答，再重新流式生成”的双回答问题。

### 完成标准

- `ChatModel` 暴露模型能力档案；
- 主模型与 fallback 模型能力兼容规则明确；
- 宿主配置使用判别联合；
- `createModel(config)` 以策略模式创建 Adapter；
- 工具调用使用明确的工具规划协议；
- Workflow 不通过 provider 名称分支。

### 03-model-provider-strategy.md

#### 具体模型能力档案

能力不能只按 Adapter 固定声明，因为不同 Ollama 模型、不同主/降级模型可能能力不同。

```ts
interface ModelCapabilities {
  streaming: boolean;
  toolCalling: boolean;
  usage: boolean;
}

interface ModelProfile {
  provider: string;
  model: string;
  capabilities: ModelCapabilities;
}

interface ChatModel extends CoreProvider {
  readonly primaryProfile: ModelProfile;
  readonly fallbackProfile?: ModelProfile;

  generate(input: GenerateInput): Promise<GenerateOutput>;
  stream(input: GenerateInput): AsyncIterable<GenerateStreamChunk>;
}
```

#### 主模型与 fallback 模型的兼容规则

```txt
- Workflow 在每次具体模型调用前使用本次有效 ModelProfile 判断能力
- 主模型失败且 fallback 接管时，必须重新评估 fallbackProfile
- 当当前阶段需要 streaming 而 fallback 不支持 streaming：不得静默假装流式；应在首 delta 前失败并发出 workflow:error
- 当当前阶段需要 tool calling 而 fallback 不支持：该轮工具规划降级为 no_tool，并在 trace / event 中标记 tool_calling_unavailable
- 宿主可选择更严格策略：factory 在初始化时拒绝“主/降级模型能力不兼容”的配置
```

V1.1 默认采用“运行时明确降级 + 可观测标记”；Demo 可增加严格校验提示，但不强制拒绝启动。

#### 宿主配置策略

```ts
type ModelConfig = OpenAICompatibleConfig | OllamaConfig;

type OpenAICompatibleConfig = {
  provider: "openai-compatible";
  apiKey: string;
  baseUrl?: string;
  model: string;
  modelProfile?: Partial<ModelProfile>;
  fallbackModel?: string;
  fallbackProfile?: Partial<ModelProfile>;
  retry?: ModelRetryConfig;
};

type OllamaConfig = {
  provider: "ollama";
  host?: string;
  model: string;
  modelProfile?: Partial<ModelProfile>;
  keepAlive?: string;
};
```

```ts
createModel({ provider: "openai-compatible", ... });
createModel({ provider: "ollama", ... });
```

#### 工具规划协议

当没有工具，或当前有效模型 `toolCalling=false`：

```txt
跳过工具规划
↓
直接进入 Final Response Stream
```

当工具存在且当前有效模型支持工具调用：

```txt
先执行 Tool Planning
↓
只允许得到：
- no_tool
- tool_calls
↓
no_tool
→ 直接进入 Final Response Stream

tool_calls
→ 执行工具
→ 将工具结果写入消息上下文
→ 进入 Final Response Stream
```

工具规划不得直接复用“最终回答生成”的结果。它必须使用独立契约，确保不会出现：

```txt
先 generate 出一段最终自然语言
↓
为了流式效果丢弃该回答
↓
再 stream 一遍不同回答
```

建议新增：

```ts
interface ToolPlanningProvider extends CoreProvider {
  plan(input: ToolPlanningInput): Promise<ToolPlan>;
}

type ToolPlan = { type: "no_tool" } | { type: "tool_calls"; calls: ModelToolCall[] };
```

V1.1 可由基于 `ChatModel.generate()` 的默认实现提供该能力，但规划 Prompt 必须只返回结构化计划，不生成面向用户的最终回复。

#### Workflow 行为分支原则

```ts
// 正确：依据本次有效模型能力
if (!effectiveModelProfile.capabilities.toolCalling) {
  // 跳过工具规划并记录降级原因
}

// 错误：依据 provider 名称
if (model.meta.id === "model.ollama") {
  // 禁止
}
```

## 阶段 4：SimpleChatWorkflow 步骤函数化重构

### 目标

在流式改造前先消除当前 `SimpleChatWorkflow` 的单体长方法，建立 execute / stream 共享的步骤函数，避免双路径漂移。

### 完成标准

- `execute()` 外部行为保持不变；
- 原有 trace、observer、降级逻辑保持不变；
- 每一步可被 execute 和 stream 复用；
- 重构单独提交、独立 review；
- 不在本阶段引入用户可见流式输出。

### 04-workflow-step-refactor.md

#### 建议提取步骤

```ts
async function runPersonaStep(...)
async function runSafetyInputStep(...)
async function runSummaryLoadStep(...)
async function runMemoryRecallStep(...)
async function runEmotionStep(...)
async function runPromptBuildStep(...)
async function runToolPlanningStep(...)
async function runToolExecutionStep(...)
async function runSafetyOutputStep(...)
async function runSummarySaveStep(...)
async function runMemoryExtractSaveStep(...)
async function buildWorkflowOutput(...)
```

#### 重要语义修正

不是所有步骤都使用聊天模型 `generate()`：

```txt
Safety:input
→ SafetyProvider.guardInput()

Summary:load
→ SummaryProvider.load()

Memory:recall
→ MemoryProvider.recall()；内部可能使用 EmbeddingProvider，但不是 ChatModel.generate()

Emotion:analyze / transition
→ EmotionEngine；其实现可能使用模型

Tool planning
→ ToolPlanningProvider；默认实现可能使用模型

Tool execute
→ ToolRegistry / ToolProvider

Final response
→ ChatModel.stream() 或 ChatModel.generate()

Safety:output
→ SafetyProvider.guardOutput()

Summary:update
→ SummaryUpdater；其实现可能使用模型

Memory:extract / save
→ MemoryExtractor / MemoryProvider；抽取实现可能使用模型
```

#### 可观测结果

```txt
- executeWorkflow 回归验证通过
- 重构前后相同输入得到等价结构化输出
- trace step 顺序、observer 事件和 memory / summary 降级语义未改变
- 当前仍无用户可见流式文本
```

## 阶段 5：工作流级流式协议与流式聊天实现

### 目标

把模型级 `stream()` 升级为 Core / Workflow 级 `streamWorkflow()`，让宿主消费完整聊天生命周期，而不仅是文本片段。

### 完成标准

- `ChatWorkflow` 新增 `stream()`；
- `CompanionCore` 新增 `streamWorkflow()`；
- `SimpleChatWorkflow.stream()` 复用阶段 4 的步骤函数；
- 最终回答真实流式输出；
- 现有 runtime、trace、summary、memory、emotion、tool 结果可在 `workflow:finish` 获取；
- 已输出文本后的异常必须明确失败；
- `execute()` 行为不受影响。

### 05-streaming-workflow.md

#### 接口扩展

```ts
interface ChatWorkflow extends CoreProvider {
  execute(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): Promise<ChatWorkflowOutput>;

  stream(
    input: ChatWorkflowInput,
    context: ChatWorkflowExecutionContext,
  ): AsyncIterable<ChatWorkflowStreamEvent>;
}
```

```ts
core.executeWorkflow(input);
core.streamWorkflow(input);
```

#### 流式编排顺序

```txt
Persona:load
↓
Safety:input
↓
Summary:load
↓
Memory:recall
↓
Emotion:analyze / transition
↓
Prompt:build
↓
Tool:list
↓
Tool:plan（仅工具存在且有效模型支持时）
↓
Tool:execute（如有 tool_calls）
↓
Final Response → model.stream() → text:delta × N
↓
Safety:output（完整文本后审计）
↓
Summary:save
↓
Memory:extract / save
↓
workflow:finish（含完整 ChatWorkflowOutput）
```

#### 输出安全边界

V1.1 仍采用完整文本后审计：

```txt
text:delta 已输出
↓
流完成，得到 completeText
↓
SafetyProvider.guardOutput(completeText)
```

若输出安全被拒绝：

```txt
- 发送 workflow:error
- Demo 明确标记“输出未通过安全审计”
- 不伪造安全回复
- 不掩盖已展示的流式文本
```

实时 token 级审计不属于 V1.1。

#### 错误语义

```txt
首个 text:delta 前失败
→ 允许模型 Runtime 重试或 fallback
→ 最终失败则 workflow:error

已发送 text:delta 后失败
→ 发送 workflow:error
→ Demo 标记 partial failure
→ 不发送 workflow:finish

写回阶段（Summary / Memory）失败
→ 按 V1.0 既有降级策略处理
→ 在 workflow:finish 的 trace / metadata 中体现 degraded 状态
```

#### 可观测结果

```txt
workflow:start
step:start / step:end
text:delta × N
workflow:finish
```

并验证：

```txt
- executeWorkflow 保持可用
- streamWorkflow 可独立消费
- 正常流结束后可获得完整 ChatWorkflowOutput
- 部分输出失败时不会被误标为成功
```

## 阶段 6：Ollama Adapter

### 目标

增加正式 Ollama `ChatModel` Adapter，使本地模型可注入 Core，而不是通过 OpenAI-compatible 模拟接入。

### 完成标准

- 新增独立 `packages/model-ollama`；
- 使用 `ollama` npm 包实现 `ChatModel`；
- 支持 `generate()` 与 `stream()`；
- 正确暴露具体模型能力档案；
- 支持 host、model、keepAlive；
- 工具调用有明确能力映射或降级；
- 与 OpenAI-compatible 使用同一 Core API；
- Demo 可切换 Provider。

### 06-ollama-model-adapter.md

#### 包边界

```txt
packages/
├── ai-core/
│   ├── ChatModel / ModelProfile / ToolPlanningProvider 抽象
│   ├── Workflow
│   └── 流协议
│
```

## V1.1 关键设计原则

1. `streamWorkflow()` 是新增 API，不替换 `executeWorkflow()`；
2. 模型级流与工作流级流必须分离；
3. Core Event 与 Wire Event 必须分离；
4. 最终用户可见回复才流式化；内部结构化任务可继续使用 `generate()`；
5. Safety、Summary Load、Memory Recall 不是默认的 ChatModel.generate 调用；
6. 工具规划与最终回答生成必须分离，禁止为了流式效果生成两段最终回答；
7. 当前有效模型的能力决定 Workflow 行为；Adapter 名称不得作为业务分支；
8. fallback 接管时必须重新评估具体模型能力；
9. Persona 是 Core 配置，不依赖用户系统；
10. 外部 SDK Adapter 独立 package，`ai-core` 保持纯 SDK；
11. 所有模型配置由宿主注入，`ai-core` 不读 env；
12. Ollama Embedding Provider 不属于 V1.1；
13. Demo 是长期调试工作台；
14. 已输出文本后的失败必须可观测，不能伪装成功；
15. Output Safety 拒绝必须可见；
16. 流式改造前必须先完成步骤函数化重构并独立 review；
17. 每阶段完成后必须留下可复现人工验证结果和 review 归档。
